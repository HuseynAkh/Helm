## Findings, ranked by severity

### P8-1 — High — undo discards the output identity and adopts a replacement before executing

**Locations:** `Sources/HelmOperations/Execute/ForwardEvidence.swift:18–30`; `Execute/OperationExecutor.swift:64`; `Execute/OperationResult.swift:15`; `Undo/UndoPlanner.swift:14–20` (all latter paths under HelmOperations).

K34 retains identities during forward execution, but the successful outcome still stores only the change token and kind. Undo has no recorded output identity. `ForwardEvidence.capture` deliberately excludes the original context for inverse plans, then reads the *current* source and adopts its identity. The token/kind check subsequently accepts a different object with matching metadata, and the new atomic mutation correctly operates on that wrongly adopted object. This is an incomplete identity integration across the journal boundary, not the previously documented race between a mutation and its immediate metadata read.

**Reproduced scenario:** execute a one-byte create at `/output`; keep its metadata in a separate fake fixture; remove and recreate `/output` with different one-byte contents and restore the recorded modification date. The replacement has a different UUID identity but the same change token and kind. Build the inverse from the real successful result and execute it. The replacement is moved to Trash and undo reports success. The same journal omission affects moved leaves and Replace's installed/backup leaves. This requires neither an inode-reuse assumption nor mutation during a preflight callback. Live executor refusal currently prevents native execution, but any provider implementing the conditional contract remains exposed.

Public-API stdin-compiled probe against the P8 build produced:

```text
undo equal tokens true different identities true successes 1 replacement remains false
```

**Exact fix:** retain the observed output `FileMutationPrecondition` (or identity alongside kind/token) in successful outcomes, carry it into inverse-plan expected evidence, and seed inverse ForwardEvidence from that recorded evidence. Never fill a missing inverse identity by reading the current occupant. Remap identity through internal moves/Trash; refuse automatic undo when evidence is absent, retaining the existing tree refusal. An atomic output receipt remains separately needed for the already disclosed observation window. Add same-token/different-identity leaf substitution tests before inverse construction and before execution, including Replace and move restoration. Existing changed-token tests and K34's substitution *after preflight* test still pass with this defect.

### P8-2 — Medium — cancellation before conditional admission permanently quarantines a clean executor

**Locations:** `Sources/HelmFileSystem/Fake/InMemoryFileSystem.swift:172`; `Sources/HelmOperations/Execute/OperationExecutor.swift:83–93`, `:182–197`; `Sources/HelmCore/Identity/FileMutationPrecondition.swift:27`.

The new conditional fake checks cancellation before comparing evidence or mutating. It throws plain `CancellationError`, which cannot communicate its guaranteed no-mutation result. The executor wraps it as `StepExecutionFailure`, marks reconciliation required and permanently sets `quarantined`. Its only subsequent response is `.busy`. The same wrapper also includes cancellation during read-only validation inside `mutate`, before a provider is even called. Conservative treatment of unknown in-flight cancellation is correct; treating known pre-admission cancellation identically loses the new boundary's useful guarantee.

**Reproduced scenario:** a conditional copier cancels its current task immediately before forwarding to `InMemoryFileSystem.mutate(.copy, ...)`. That method throws at its first check, with no output created. After awaiting the cancelled task, execute an unrelated create on the same executor from an uncancelled task. It returns `.busy`, with no reset API. Probe output:

```text
cancel Optional(HelmOperations.OperationError.cancelled) reconciliation Optional(true) output exists false next Optional(HelmOperations.OperationError.busy)
```

This models cancellation arriving at the actor hop/admission boundary; the test copier performs no mutation and forwards the original evidence unchanged. It differs from P2-1/F2's deliberately conservative handling of cancellation *after* native entry.

**Exact fix:** add a typed cancelled-before-mutation refusal to the conditional contract and have providers emit it only while they can guarantee zero effects. Map it to `.cancelled` with no reconciliation/quarantine. Separately keep read-only preflight cancellation outside the mutation-uncertainty wrapper, or carry explicit admission state in that wrapper. Preserve quarantine for ordinary cancellation errors from a possibly-started primitive and preserve successful started work. Add a gated cancellation-before-admission test asserting zero effects, no reconciliation, and a successful next operation on the same executor; retain the existing started-copy and timeout controls. K34's refusal tests cover unsupported/sourceChanged, not this cancellation result.

## Scope conclusions and cancellation behavior

- Forward manifest identities now reach conditional copy/move/Trash. The fake compares evidence and mutates without suspension; it cannot accept a swapped source between those actions. Live deliberately inherits unsupported mutation, so this is a safety refusal, not native F-052/F-053/F-054 parity. No recommendation to replace it with stat-then-mutate.
- A forward operation can still adopt a substituted output during the already documented post-mutation metadata window. Root evidence still cannot detect all changed descendants or same-object same-token content edits. These are inherited P6-1/K34 limitations, excluded from the new count.
- BatchRenamePlanner is pure. A throwing cancellation hook unwinds local arrays and returns no partial plan or filesystem effects. Temporary-name probes propagate even a one-shot custom error instead of converting it to an invalid-name issue. Sorting and a per-directory union remain indivisible CPU segments; their boundedness is not a promise of immediate cancellation.
- BatchRenameWorker retains one active calculation and at most one pending revision; replacement/disappearance cancel them, and cancelled results are rejected. The adapter checks cancellation around evaluation and revision before execution. The locked cache has synchronized access; no new unchecked-Sendable race was established. Native SwiftUI lifecycle/typechecking still needs macOS review.
- Cancelling an already executing rename/Replace is intentionally not transactional: earlier primitives remain journaled, later steps are not attempted, and temporary names can remain. This is the specified B-038 partial-result behavior. Pure preview cancellation does not perform those steps. Automatic undo must not bypass the evidence requirements in P8-1.
- F7's exact original replacement spelling, linear cut-completion extraction, and multi-volume timeout admission remain present. Existing tests exercise those fixes; they are not repeated as findings.
