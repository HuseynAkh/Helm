## Findings, ranked by severity

### P6-1 — high — forward mutations never acquire source or intermediate-artifact preconditions

**Locations:** `Sources/HelmOperations/Plan/OperationPlanner.swift:30`, `:176–180`; `Sources/HelmOperations/Execute/OperationExecutor.swift:56–63`, `:117–133`, `:178–190`, `:219`.

Ordinary plans leave `expectedTokens` empty. `validateExpectedSource` returns successfully when the token is absent and the policy is `.none`. The source manifest is consulted only by copy verification, not by ordinary Trash, rename, or same-volume Move. Moreover, successful forward copies/moves do not add newly created stage/backup objects to the executor's expected-token map: its remapping block runs only when the source already had an expected token. Thus later destructive steps trust a pathname even when a prior primitive established an object at that path.

**Concrete failing scenario:** build a same-volume Move or Trash plan for `/work/report` containing one byte. Before its progress callback returns, another process moves the selected file aside and creates a different, two-byte file at `/work/report`. Execution moves/trashes the replacement and reports success. The collected manifest contains sufficient evidence to reject this obvious change, but it is ignored. No narrowly timed stat/syscall race is needed.

**Replacement variant:** execute Copy Replace through stage verification and moving the old target into `.helm-backup-report`. Before the backup-Trash step, move that backup aside and create an unrelated file at its old pathname. The executor trashes the unrelated file without checking the token it recorded when creating the backup. Similarly, changing the stage after verification and before installation installs an unverified stage. Progress callbacks provide deterministic boundaries for each text-only repro; current replacement boundary tests inject failures, not successful substitutions.

**Exact fix:** introduce per-primitive forward preconditions, distinct from undo's leaf-only policy. Seed selected source evidence from the manifest; snapshot the existing replacement target as well. Track successful stage/backup identity and change evidence, remap it on internal moves, and require it immediately before each dependent mutation, after callbacks and preflight. Missing evidence must stop a dependent destructive step for reconciliation. Use a native identity-aware mutation seam to close the remaining narrow compare/mutate race; at minimum reject changed kind/token now. Do not simply enable `.leafOnly` on every forward plan, which would disable legitimate directory moves and Trash. Add replacement-at-progress tests for plain Trash, same-volume Move, backup Trash and stage installation.

**New versus P2-4:** P2-4 covered stale checks on inverse plans that already carry expected tokens. F2 repairs that path. This finding is the complete absence of forward checks and of ownership tracking for generated intermediates; F2's recheck cannot help when its token map is empty.

### P6-2 — high — a cross-volume copy quarantines the source queue but leaves its destination writable

**Locations:** `Sources/HelmFileSystem/Live/LiveFileSystem.swift:27–34`, `:92–101`; `Sources/HelmFileSystem/Live/IOExecutor.swift:46–54`.

`copyItem` registers the entire native operation under `queueKey(source)` only. On timeout IOExecutor quarantines that one key. The native operation can still write to the destination volume, yet that destination's queue remains available. A destination that was already quarantined is likewise never consulted when a fresh copy enters from another source volume.

**Concrete failing scenario:** share one LiveFileSystem/IOExecutor across two existing window executors, as allowed by the module's per-window integration notes. Window A copies `/Volumes/A/tree` to `/Volumes/B/tree`; the copy blocks after creating part of the output and times out. A is quarantined; B is not. Window B can immediately rename/trash `/Volumes/B/tree` while the original native copy is still running. No recreation of the quarantined OperationExecutor is required. Alternatively, after B is quarantined by a B-local stalled call, a copy from A into B can still enter native I/O because admission checks only A.

**Exact fix:** register every involved volume with a shared mutation-admission/quarantine mechanism. Cross-volume copy must atomically check both source and destination admission, register its pending/running state with both, and quarantine both if completion becomes uncertain. Scheduling may choose one worker queue, but queue selection must not determine the entire safety footprint. Apply the same rule to multi-path native methods. Add a gated two-volume test proving that destination work is refused after timeout, copying into an already-quarantined destination is refused before body entry, and a truly unrelated third volume still works.

**New versus R1-1:** F5 correctly makes queued admission atomic for a supplied volume key. This is a caller-side missing-volume problem; the repaired lock cannot quarantine a destination never supplied to it. The risk remains even when all callers share the same IOExecutor. Real macOS cross-volume blocking behavior still needs native validation; the incorrect admission footprint is directly visible in portable source.

### P6-3 — medium — Replace undo restores the incoming filename's case, not the original target's case

**Locations:** `Sources/HelmOperations/Plan/OperationPlanner.swift:139–155`, `:178`; `Sources/HelmOperations/Undo/UndoPlanner.swift:32–34`.

Collision detection folds names using destination semantics, but replacement constructs `target` from the incoming source's basename. It never recovers the actual colliding name from `context.existingNames`. The backup move therefore journals a source spelling that may never have existed as a directory entry. Undo faithfully restores that fabricated spelling.

**Concrete failing scenario:** use `InMemoryFileSystem(caseSensitive: false)` with source `/src/report.txt` and existing target `/dest/REPORT.TXT`, each a regular file with distinct bytes. Build and execute Copy Replace with an origin store shared with UndoPlanner; then execute the inverse. The old target bytes return under `report.txt`, whereas the pre-operation directory contained `REPORT.TXT`. Assert the actual child-name set, not just `exists(uppercaseURL)`, because case-insensitive lookup makes the latter pass. The same issue applies to canonically equivalent names whose original spelling differs.

**Exact fix:** retain a folded-key-to-original-name mapping for destination snapshots. Represent the old target URL separately from the incoming installed URL; move the old target using its actual spelling and journal that exact origin. Undo must restore the original spelling. Revalidate the collision object's identity at execution as in P6-1. Add a case-insensitive replacement round trip checking original bytes and exact child names; retain the existing case-only rename tests as separate coverage.

**Why new:** P2-5/F2 fix containment under case semantics; they do not preserve the spelling of the replaced item. This is a B-042-style wrong-name undo, not a request to change the chosen spelling of the newly installed file.

### P6-4 — medium — cut completion does a quadratic scan after the repaired large batch finishes

**Location:** `Sources/HelmOperations/Execute/OperationResult.swift:35–39`; consumer contract in `Sources/HelmOperations/Clipboard/ClipboardTransaction.swift:24–30`.

`completedMoveSources` filters every command source by scanning outcomes from the beginning. For 100,000 successful one-step moves in source order, this performs 5,000,050,000 predicate visits; each access repeats the work. The synchronous computed property can stall the caller while preparing clipboard acknowledgment, even though F2/F5 fixed planning and journal complexity.

**Concrete failing scenario:** construct a result containing 100,000 distinct Move sources and one successful move outcome per source, in matching order. Access `completedMoveSources` once before acknowledging the cut. All answers are correct, but the nested scan performs the quadratic number of visits above. The existing 100k planner/journal regression never accesses this property, and the partial-cut tests use small arrays. F5's production work counters cover planner and journal work, not this result transformation.

**Exact fix:** collect successful `.move`/`.trash` outcome sources into a set in one pass, then intersect with a set of original command sources. Preserve the existing command-kind guard and partial-failure semantics. Add a production-integrated visit-count test for 100k outcomes with failed and unrelated intermediate steps; require linear visits and the same completed-source set. Avoid a fragile wall-clock threshold.

**New versus P2-7/R1-4:** neither earlier finding identified or measured this post-execution result path. The repaired planner/journal work remains linear for their covered inputs.

## Fix interaction and non-findings

- F2's started-call cancellation behavior and F5's shared admission lock are compatible: queued cancellation prevents body entry, while an already-started body retains its actual result. No new exactly-once continuation defect established.
- F2's exclusive-write failure path retains artifacts and does not reintroduce the unsafe unlink. Enumeration still throws on metadata failures. Replacement containment checks remain present.
- K29's current `.leafOnly` guard rejects directory/package undo during the initial validation pass as well as immediately before mutation. The earlier missing-descendant-evidence issue is not counted again. Missing metadata continues to prevent unsafe inverse construction/execution.
- Whole-tree byte cancellation, strong content hashing, native stat/mutate races, durable journals, and directory undo are already documented limitations. Cross-volume dependent steps deliberately do not rename themselves on collision; that documented limitation is not counted as a fresh defect here.
- Repeated incoming basenames under Replace deserve an explicit product-policy test, but Apply to All may intentionally authorize sequential replacement; this report does not elevate that ambiguity into a proven defect.
- No macOS SDK compile/API defect is claimed from Linux inspection. Trash, metadata/resource-value behavior, and native copy/rename completion require macOS acceptance.
