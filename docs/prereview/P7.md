## Findings, ranked by severity

### P7-1 — blocker — Batch rename adapter does not handle Core's overlap issue

- **Location:** `Sources/HelmUI/Sheets/BatchRenameViewModel.swift:53`; contract at `Sources/HelmCore/Naming/RenamePair.swift:23`.
- **Wrong:** The exhaustive switch over `BatchRenameIssue` omits `.overlappingSources(URL, URL)`. The portable HelmUI module fails to compile, independently of SwiftUI or SDK availability.
- **Concrete failing scenario:** Compile the portable UI adapters against current HelmCore. Swift reports `switch must be exhaustive`, with `add missing case: '.overlappingSources(_, _)'`. A user selecting a directory and its descendant for batch rename is precisely the new validation case the UI must explain.
- **Exact fix:** Add `case let .overlappingSources(ancestor, descendant)` to the message mapping and display both paths, explaining that a folder and an item inside it cannot be renamed in the same batch. Keep the plan non-executable; do not remove the Core case or add a silent default. Add an adapter test with `/fixtures/folder` and `/fixtures/folder/child.txt`, asserting an overlap message, `canRename == false`, and no executable plan.
- **Reproduction:** Build HelmSearch, HelmOperations, HelmPersistence and HelmTestKit using `/tmp/build-P7`, then run `HELM_UI_SCRATCH=/tmp/build-P7 python3 Tests/HelmUITests/PortableRunner/run.py`. The failure occurs when emitting HelmUI, before XCTest execution. A direct repeat after the required wait is recorded below.
- **Coverage gap:** Existing adapter tests cover duplicate sources and destination collisions but not ancestor/descendant selections. Root SwiftPM tests omit HelmUI entirely, so passing Core tests and static checks cannot catch this cross-module switch mismatch.

### P7-2 — medium — Superseded and dismissed sheets leave full rename planning running

- **Location:** `Sources/HelmUI/Sheets/BatchRenameSheet.swift:51–60`, especially the detached task at line 56; synchronous work at `BatchRenameViewModel.swift:30` and `Sources/HelmCore/Naming/BatchRenamePlanner.swift:13–106`.
- **Wrong:** SwiftUI cancels the outer `.task(id:)` on edits/disappearance, but cancellation does not propagate into `Task.detached`. Its handle is immediately awaited and never cancelled. Once the 150 ms debounce expires, the complete planner runs even if its result can no longer be used. The later cancellation/revision check correctly prevents stale publication; it does not stop CPU work or release the captured selection and intermediate plan. The planner has no cancellation checks.
- **Concrete failing scenario:** Open batch rename for 100,000 entries; let evaluation start, then change the prefix several times with pauses longer than 150 ms while earlier plans are still running, and dismiss the sheet. Each accepted revision can retain a separate full plan calculation running at user-initiated priority after dismissal. CPU/memory cost scales with the number of unfinished revisions. No stale rename execution or data loss is claimed; the defect is uncancelled resource consumption. Source proves the lifetime; duration and peak memory need macOS measurement.
- **Exact fix:** Give evaluation an explicitly owned worker handle, forward outer-task cancellation using `withTaskCancellationHandler`, and cancel on replacement/disappearance. Make the planning operation cooperatively cancellable, checking cancellation during name generation, occupancy/target construction and temporary-step generation, and before/after sorting. Return cancellation without caching a partial plan. A handle cancellation alone is insufficient while the planner ignores cancellation. Bound concurrent evaluation to one worker with at most the latest pending revision, retaining the existing revision guard before display/execution.
- **Coverage gap:** `testEditsInvalidateCopiesAndRejectObsoleteCompletion` computes both revisions synchronously and checks only which result is executable. It passes if every obsolete worker runs to completion. Add an injected slow evaluation worker test that starts A, replaces it with B, dismisses the owner, and asserts cancellation reaches A/B, no result is published after teardown, and the concurrency bound holds.
