## Findings (ranked)

### P18-1 — Medium — Successful drop is mistaken for changed destination identity

**Location:** `Sources/HelmCore/SpringNavigation/SpringNavigationSession.swift:74` (related full-entry comparisons at lines 27 and 44).

**Wrong:** `destination == request.target` compares every FileEntry field, including modification date, size, child count and star state. Successful insertion into a directory normally changes its metadata. The completion therefore calls `cancel()` and restores the original context even though the operation succeeded. Conversely, equal metadata with absent objectIdentity is not proof against replacement. Request UUIDs protect callback generations, not filesystem object identity.

**Concrete failing scenario:** Accept a copy into `/destination` with childCount 0. Report success with fresh metadata for that same directory, now childCount 1 and a newer modification date. The local probe emitted `.restore(original)` instead of `.commit(destination)`. The existing success test supplies the unchanged pre-operation entry; the changed-destination test explicitly expects restoration for a size-only change, reinforcing the conflation.

**Exact fix:** Separate stable destination identity admission from mutable metadata equality. Retain the accepted URL/kind and object identity; accept completion for the same identity despite changed content metadata, and reject different identities. Where trustworthy identity is unavailable, define an explicit unverified/revalidation result rather than using full-entry equality as identity proof. Have the executor supply its verified destination evidence. Add a same-object successful-drop test with changed mtime/childCount and a different-object test with otherwise identical metadata. Apply the same identity-versus-presentation distinction to hover refreshes so starring or refreshing a hovered folder does not repeatedly restart its deadline.

### P18-2 — Medium — Spring navigation admits remote/decorated file URLs

**Location:** `Sources/HelmCore/SpringNavigation/SpringNavigationSession.swift:26` and `:63`.

**Wrong:** `isFileURL` alone admits remote authorities, credentials and query/fragment decorations. The reused DropSession/DropPlanner does not supply the stricter local-URL admission used by the new CloudPolicy/Sharing/PathPresentation components. This emits load/drop intents for unsupported addresses; it is not evidence that an operation was actually executed.

**Concrete failing scenario:** A directory FileEntry with `URL(string: "file://server/destination")` produces one `.load` effect and a non-nil accepted drop for a local `/source/file`. Both results were reproduced. A host that turns the URL into `.path` can then reinterpret the remote address as a local destination. Existing spring tests reject virtual locations but do not exercise remote or decorated file URLs.

**Exact fix:** Validate target and source URLs at the spring boundary before hover loads or drop acceptance: require file scheme, absolute path, nil/empty/localhost host, and no user/password/port/query/fragment. Retain a source-validation result from initialization and refuse drop acceptance on failure. Use the same policy as the scoped local-URL planners. Add remote/decorated source and destination cases, ordinary non-file URLs, and accepted localhost controls; assert no load/accepted intent is produced for rejected targets.

### P18-3 — Medium — “Lexical/no I/O” normalization resolves real symlinks

**Location:** `Sources/HelmCore/PathPresentation/PathPresentation.swift:17`, `:66`, `:84`; `Sources/HelmCore/Sharing/SharingRequest.swift:16`.

**Wrong:** Foundation `standardizedFileURL` is not a guaranteed filesystem-independent lexical normalizer. For paths containing `..`, it can resolve symlinks. PathPresentation explicitly promises to preserve symlink spelling and avoid filesystem probing, but its ancestry and deduplication can depend on the actual filesystem. Sharing also replaces the captured input URLs with these normalized values. The existing “symlink” test only labels a fabricated FileEntry as a symlink; no symlink exists, and the tested dot segment is `.` rather than `..`.

**Concrete failing scenario:** In a temporary fixture, `link` points to `real/child`. Supplying `link/..` produces ancestry ending in `real` and a Sharing snapshot containing `real`, rather than retaining the supplied spelling. This was reproduced on the installed Linux toolchain. The related `link/../x` normalized lexically to the fixture's `x`, illustrating that normalization is not a reliable physical traversal policy either. Pure presentation should not silently decide physical symlink traversal or probe a potentially stalled mount.

**Exact fix:** Introduce an explicitly lexical component policy for presentation identities, implemented without `standardizedFileURL` or existence-inferencing URL constructors. Pass explicit directory hints when constructing URLs. For action-bearing sharing URLs, preserve the validated supplied URL; use a separately defined safe deduplication key, and either preserve or explicitly reject ambiguous parent components rather than silently retargeting them. Document the chosen `..` policy. Add real temporary-symlink regressions, including a missing final component, and assert both displayed spelling and action URL. Reconcile this with shared ItemID normalization before integration; changing labels alone is insufficient.

### P18-4 — Medium — Directory hints break path segment intent lookup

**Location:** `Sources/HelmCore/PathPresentation/PathPresentation.swift:47` and `:70`.

**Wrong:** Ancestry reconstructs URLs without the supplied directory hint, then matches whole Foundation URLs. `/folder/` and `/folder` remain unequal after standardization even though this module otherwise identifies items by standardized path. URL construction can infer its hint from filesystem existence, making lookup depend on whether the directory exists locally.

**Concrete failing scenario:** Build a directory projection using `URL(fileURLWithPath: "/P18-absent-directory", isDirectory: true)`. Request `.navigate` using that exact input URL. The projection contains the directory segment, but returns nil. The local probe reproduced this. This also affects metadata-only fixtures, stale/offline folders, and callers using known directory metadata. Existing tests create URLs with the same default initializer on both sides and therefore mask the distinction.

**Exact fix:** Use the canonical validated path identity for segment membership, independently of directory hints; construct output URLs with the segment's explicit `isDirectory` value. Normalize localhost consistently if accepted. Preserve the URL authority validation before comparing paths. Add tests for both directory hints, absent and present folders, and ensure an unrelated path remains rejected. Using IDs returned directly by the projection is a host workaround, not a repair of the public URL lookup contract.

### P18-5 — Medium — Gallery page navigation uses thumbnail demand as page size

**Location:** `Sources/HelmCore/Gallery/GalleryState.swift:39`.

**Wrong:** `viewport.indices(...).count` includes prefetch and is capped by the request budget. Keyboard page movement consequently depends on an imaging tuning knob, not the visible filmstrip extent. With rendering requests disabled it moves only one item even when a full page is visible.

**Concrete failing scenario:** With 100 entries, selected index 0, width 192 and default extent 96, Page Down moves to index 2 for prefetch 0, index 4 for prefetch 2, and index 99 for prefetch 128. All three were reproduced with identical visible geometry. The keyboard test covers only Home/End/Left/Right, and the 100k test only counts requested images.

**Exact fix:** Expose a finite, overflow-safe visible-cell/page count derived from geometry independently of prefetch/requestLimit, and use it for Page Up/Down. Keep the bounded demand range solely for imaging requests. Test invariant page movement across prefetch 0/2/128 and requestLimit 0/1/128/512, including clipped end pages and nonfinite geometry.
