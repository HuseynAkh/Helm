## Findings, ranked by impact

### P10-1 — medium — reverting a whole-mode permission draft revives an older row edit

**Locations:** `Sources/HelmCore/Inspector/InspectorEditModel.swift:41`, `:46`, `:73`; `Sources/HelmCore/Inspector/PermissionsModel.swift:40`.

There are two independent draft stores. Whole-mode drafts override row edits in `value(for:)` and `makePlan`, but `set` removes a whole-mode draft when it equals the originals without clearing those older row edits. Consequently, explicitly returning permissions to the original mode can produce a different chmod intent. The README's explicit-draft precedence is not maintained for this value.

**Failing scenario:** start with one editable item at `0644`; set the owner row to `7`; set the whole mode to `0600`; then set it back to `0644`. The last call removes `pending[.permissions]`, exposing the old owner edit. `value(for: .permissions)` is `0744`, `isDirty` remains true, and `makePlan` proposes `0744` despite the final explicit `0644` request. No executor is needed to observe the incorrect plan.

The same split also makes the row presentation disagree with a whole-mode draft: immediately after setting `0600`, `permissions.row(.owner)` still reports `7`, while the plan uses `6`. A permissions UI consuming the documented row API therefore does not show the mode it will submit.

**Exact fix:** establish one effective permission draft. When assigning a whole mode, supersede/clear prior row edits (preserve the separately chosen recursive flag), including when that mode equals the originals. Derive permission rows from the same effective modes used by `value` and `makePlan`. Route subsequent row changes through the owning edit model with an explicit rule for superseding or modifying a whole-mode draft; avoid two independently mutable authoritative stores.

**Missing regression:** `testPermissionDraftOverridesRowsAndCanReset` only tests a non-original override followed by `reset`, whose implementation clears both stores. Add row edit → whole-mode edit → explicit original-mode assignment and assert an empty nonrecursive plan, clean state and original rows. Also assert row/value/plan agreement while the override is active, and preservation of separately selected recursive intent.

### P10-2 — medium — permission rows hide unknown members of a multi-selection

**Location:** `Sources/HelmCore/Inspector/InspectorEditModel.swift:19` and `Sources/HelmCore/Inspector/PermissionsModel.swift:40`.

The initializer drops items lacking permission metadata with `compactMap`. Row aggregation then describes only the readable subset as if it represented the full selection. The outer model correctly returns `.unavailable` for the permissions field, but its public permissions rows report concrete access. Disabling edits with `canEdit` does not correct the false displayed value.

**Failing scenario:** select A with `.permissions(0o644)` and B with no permissions attribute, for example an unavailable provider item. `value(for: .permissions)` is `.unavailable`, while `permissions.row(.owner)` is `.value(read: true, write: true, execute: false)` and the other rows also report definite values. The user is told permissions are uniform despite B being unknown. Planning still fails closed; this finding is incorrect presentation, not an observed unauthorized write.

**Exact fix:** retain metadata completeness when constructing the permission model. Return `.unavailable` for an aggregate row whenever any selected item's mode is unknown, consistently with the outer field aggregation. An additive completeness flag or optional modes can represent this; keep the existing known-only initializer for standalone callers if required. Define explicit-draft display separately from the unknown originals, and retain the current unsupported-item planning rejection.

**Missing regression:** existing tests cover an entirely empty `PermissionsModel` and a missing *comment* field, not known-plus-unknown permissions. Test both selection orders, all three rows, the outer value, `canEdit`, and rejection of a row edit/recursive plan. A two-known-item mixed-mode control must remain mixed.

### P10-3 — medium — package rows announce directory metadata bytes as package size

**Location:** `Sources/HelmCore/Accessibility/RowDescription.swift:21`; supporting classification at `Sources/HelmCore/Model/FileEntry.swift:69` and `Sources/HelmFileSystem/Live/MetadataReader.swift:33`, `:40`.

The size guard uses `isDirectoryLike`, a navigation predicate that intentionally excludes packages so they open/preview rather than navigate. A package is nevertheless a directory for size purposes. The live reader classifies a directory as `.package` on macOS and supplies its ordinary `.size` attribute, without recursively totaling its files. Standard/detailed speech presents that number as package size, violating the adjacent comment's reason for suppressing directory sizes.

**Failing scenario:** an application bundle contains 200 MB of files and its directory entry reports 4096 bytes. A `.package` FileEntry with that metadata produces `App.app, package, 4.1 KB` under en_US formatting. VoiceOver receives a misleading size even though no recursive total exists. This is established from the classification/formatting path, not a claim that the particular metadata value was measured on macOS. Legacy F-050 already lacked recursive totals; Opus audit C-22 explicitly corrects claims about those totals.

**Exact fix:** suppress raw metadata size for `.package` as well as navigable directories in `RowDescription`. Do not broaden `isDirectoryLike`, which would change package navigation. If package totals are later available, pass a separate known aggregate size rather than treating directory metadata as that total.

**Missing regression:** `AccessibilityTests.testAllRowKindsAndDirectorySizes` derives its expected answer from the exact same `!entry.isDirectoryLike` predicate, so it codifies this bug. Use an independent expected table: directory, directory symlink and package omit raw size; a regular file retains it. Test standard and detailed verbosity with a package metadata size that differs from a supplied fixture's conceptual contents.

## Other reviewed risks and limits

- Permission labels intentionally describe read/write independently of execute, as documented. Execute-only producing `No Access` is misleading if displayed alone, but this API explicitly requires a separate execute control; no unsupported claim about effective ACL access is made here. Native UI acceptance must check both controls are exposed. The old properties model spelled out Read/Write/Execute independently.
- Recursive intent with an unchanged parent produces a plan, and non-directory or unsupported selections are rejected. Child enumeration, no-follow handling, special-bit policy, undo originals and overlapping selected subtrees remain future executor responsibilities explicitly documented in the README. These are not counted as newly implemented executor defects.
- `fr_FR` and `ar` digits, grouping and absolute dates use injected locale/calendar/time zone; relative days use the injected clock. English surrounding phrases, English plural choice and English units are explicitly disclosed localization limits, not full Arabic/French support. Mixed-direction text is passed through without bidi isolation; hosted RTL/VoiceOver behavior and a future localization catalogue remain unverified. Existing Arabic exact-string tests establish the current English policy, not Arabic plural correctness.
- Identifier hex components are delimiter-safe and stable for fixed ItemID/scopes. Callers must supply distinct window/tab scopes as documented. No new collision was established. Operation milestones retain suppressed progress for later reports, terminal events bypass throttling once, and the clock-rewind policy is explicit; no new throttling defect established.
- K29 column request ownership/single-use generations address P1-4's ABA callback scenario; drag sessions cache overlap validation and release source paths on end. These earlier findings are not repeated. Content/Commands still have documented host wiring and planned-command limitations. No new actor race, unstructured task or unsafe Sendable issue was established in these pure value models.
