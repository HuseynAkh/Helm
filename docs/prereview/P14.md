## Findings, ranked by risk

### P14-1 — Medium — F14 ordering test never establishes that validation succeeded or failed as intended

**Location:** `Tests/HelmCoreTests/StoreTests/F14MonitorOrderingTests.swift:37–45`.

The test delivers the current validation reply, then takes whatever snapshot is
present as its expected baseline. It checks only that old replies do not change
that baseline. Dropping every monitor-work completion, including the valid one,
satisfies these assertions while leaving the initial empty directory on screen.
In the successful branch, validation also changes watch generation, so rejection
of the old reload alone does not isolate the new work-generation protection.

**Concrete failing scenario:** a callback wrapper accidentally discards both
current success and current failure. This test passes with an empty ready snapshot
instead of `new` or a visible `missing` error. F14's separate recovery integration
does exercise successful publication, but does not supply the missing failure
oracle in this test. The F14 report's claim of checking phase/entries needs this
qualification: they are compared to observed state, not independently expected state.

**Exact fix:** before recording the baseline, assert `[new.id]` and `.ready` for
success, and the exact `.failed(.other("missing"), attempted: tab.location)` for
failure. Assert the accepted snapshot changed from the initial one. Add two
ordinary reloads on one unchanged watch generation, reverse their replies, and
assert only the latest work identity is accepted. Retain stale success AND failure.

### P14-2 — Medium — cancelling the watch masks a broken reload cancellation handle

**Location:** `Tests/HelmFileSystemTests/LoadingTests/K34MonitorAdapterTests.swift:39–44`.

The test cancels both `reload` and `watch`, then observes silence for 50 ms. Watch
retirement independently suppresses reload success. A reload handle whose cancel
closure does nothing can therefore pass. The short inverted expectation also
does not establish that the underlying operation reached its publication boundary.

**Concrete failing scenario:** reload cancellation is removed, but watch identity
checking remains. This test still passes, while replacing reloads on a live watch
leaves obsolete work running. A delayed result beyond 50 ms can also escape the check.

**Exact fix:** unwrap both handles; keep the watch alive; gate a reload after its
read starts; cancel only the reload; release the read; await a worker-completion
acknowledgement and assert zero callbacks. Then run an uncancelled reload through
the same watch and assert its expected snapshot. Test watch retirement separately.

### P14-3 — Medium — the concurrent-flush test repairs the disk before inspecting it

**Location:** `Tests/HelmPersistenceTests/T2PreferenceTests.swift:157–158`.

After all concurrent flushes finish, a final serial `s.flush()` rewrites the latest
in-memory state. This can repair an older snapshot that incorrectly overwrote a
newer revision. The task group's scheduling order is unspecified, so `i == 39`
is not itself a valid oracle for the last admitted edit either.

**Concrete failing scenario:** remove stale-revision protection from the file
writer and arrange an old captured save to arrive after the newest save. The last
serial flush hides the corruption and restored state still equals `s.options`.
K33PreferenceDocumentTests independently checks reversed revisions at the file
actor, which is valuable; this finding is about T2's additional store-level
concurrency claim, not a claim that the entire suite misses that simple mutation.

**Exact fix:** record the last edit admitted on MainActor, gate old/new captured
saves to force reverse admission, await both, and reopen immediately without a
repairing flush. Assert the exact last-admitted value and persisted revision
behavior. Keep a separate test for explicit flush repairing/retrying an error.

### P14-4 — Medium — concurrent FIFO test verifies only the final toggle

**Location:** `Tests/HelmCoreTests/T2StoreTests.swift:144–152`.

Eight producers each send 1,000 alternating grid/list values. The assertions count
all publications and check only the final `.list` for each tab. Reordering any
interior actions while preserving the final action and total count passes.

**Concrete failing scenario:** a mailbox swaps the second and third action from
one producer. Users see a different intermediate view sequence, but sequence 8008
and the final view modes are unchanged. The separate 100k single-producer test
checks every publication; it does not exercise concurrent producer admission.

**Exact fix:** subscribe before enqueueing and record per-tab delivered actions or
uniquely identifiable resulting states. Assert every producer's entire ordered
sequence, with no duplicates or omissions, while allowing arbitrary interleaving
between producers. An injected effect recorder with unique navigation targets is
one option; avoid requiring a global order that the contract does not promise.

### P14-5 — Medium — batch-size tests cannot detect loss of progressive publication

**Location:** `Tests/HelmFileSystemTests/T2LoadingTests.swift:62–100`.

All four batch-size variants collect the stream but inspect only its terminal
snapshot. Returning a correct terminal snapshot with no progress publications
passes. Publishing and sorting after every input batch also passes. The 100k
fixture supplies one huge batch plus 100 duplicate entries, so it does not stress
the many-small-batch path or establish geometric publication work.

**Concrete failing scenario:** remove the `loadProgress` emission or replace the
geometric threshold with a constant. These tests retain correct final counts and
endpoints, while initial display is delayed or cumulative sorting becomes excessive.
This is separate from R1-4's operation-planner/drop work-budget finding.

**Exact fix:** feed batches through an acknowledged gate while a consumer is
already waiting. Assert an early cumulative snapshot before releasing EOF, its
phase, generation, full entries and later replacement metadata. Measure producer
snapshot-build counts for many single-entry batches and enforce the documented
geometric bound. Do not count received events alone: bufferingNewest(1) can
legitimately drop intermediate snapshots. Keep the terminal correctness tests.

### P14-6 — Medium — rename worker tests omit normal success and pending-request replacement

**Location:** `Tests/HelmUITests/SheetsTests/K34BatchRenameWorkerTests.swift:7–34`.

The first calculation is cancelled; the second is allowed to start and then is
also cancelled. No third request ever replaces a pending request, and no worker
request returns successfully. A completion path that always resumes its caller
with CancellationError passes these cancellation assertions. So does a worker
that queues every pending request instead of retaining only the latest, because
the test never creates more than one pending request.

**Concrete failing scenario:** typing A→B→C while A is blocked runs obsolete B
after A, or normal completion is incorrectly treated as cancelled. Both defects
escape the two current worker tests. The probe's cancellation counter increments
on every exit, including timeout/error; the error assertions help, but the counter
alone is not evidence of cancellation delivery.

**Exact fix:** gate A so it cannot exit immediately upon cancellation; admit B
then C while A remains active. Require B to finish cancelled without entering its
work closure, release A, and require C to return a distinct successful evaluation
exactly once with maximum concurrency one. Add uncancelled success/cache checks
and cancellation of the outer caller independently of `cancelAll`. Replace the
wall-clock polling loop with explicit gates and a bounded XCTest watchdog; keep
cleanup able to release gates even after a failed assertion.

### P14-7 — Low — cache equivalence tests pass when caching is disabled

**Location:** `Tests/HelmFileSystemTests/T2DirectoryLoaderTests.swift:18–32`.

Comparing equal listings on an unchanged fake establishes output equivalence,
but not a cache hit or separation of cached partitions. Always enumerating fresh
passes both tests, making every revisit of a large directory expensive.

**Concrete failing scenario:** bypass cache lookup entirely. Both hidden and
visible counts remain correct and all equality assertions still pass.

**Exact fix:** wrap the provider with separate counters for root validation and
enumeration. Require validation on every access, no additional enumeration on an
eligible hit, distinct hidden/sort partitions, and another enumeration for
`useCache: false` or invalidation. Retain the permission-denied test so the
performance assertion cannot accidentally authorize skipping access validation.

## Twenty most valuable missing tests, in priority order

These are additive acceptance cases, not twenty additional findings. They include
stronger variants of the seven findings and combinations not established by the
current suites. Scenarios are text only as required by this lane.

1. **F13 refusal has zero physical effects:** for substituted installed and backup leaves, compare contents, identities and complete source/stage/output/backup/Trash inventories before and after refused undo; `succeededCount == 0` and existence alone are insufficient.
2. **Identity substitution between inverse steps:** gate the second conditional inverse, substitute its source with equal-token/different-identity data after initial whole-plan validation, and require refusal plus preservation of the already journaled first inverse.
3. **Clean cancellation through Move/Trash executor integration:** cancel at admission, assert unchanged source bytes/identity, no new Trash origin or successful outcome, no reconciliation, and a successful subsequent operation. Current F13 executor cancellation injection is copy-focused.
4. **F14 current reply acceptance:** assert exact fresh entries or exact failure before any stale reply, as in P14-1; a drop-all-completions implementation must fail.
5. **Same-watch reload ordering:** R1→R2→R2-result→R1-success/failure with unchanged watch generation; assert R2 survives, isolating work identity from watch retirement.
6. **Changes arriving during validation:** gate V, mutate the directory and send rescan during V, return V's earlier listing, and require post-start reconciliation to publish the later contents without another external event.
7. **Cancellation during monitor retry delay:** gate the injected retry delay, close the tab or shut down, release it, and assert no further monitor factory call, callback or retained watch; acknowledge cleanup.
8. **Old monitor cleanup after replacement:** hold old stop/start completion, install a new lifetime, release the old cleanup, then prove the new monitor still delivers changes and is stopped exactly once at teardown.
9. **Native root-object replacement on Mac:** move the watched directory aside, create a new object at the same path, change its child, and verify rebind plus correct displayed entries despite delayed old vnode/FSEvents callbacks. Use an isolated temporary fixture and bounded acknowledgement.
10. **Reload-only cancellation:** keep its watch live, cancel a gated in-flight reload, await termination, assert silence, then prove an uncancelled reload on that watch succeeds (P14-2).
11. **Worker normal success:** a distinct successful evaluation reaches the caller exactly once and fills/reuses the intended cache; a worker that always reports cancellation fails.
12. **Worker A/B/C pending replacement:** block A, admit B and C, assert B never runs and only C succeeds after A ends, with maximum active work one (P14-6).
13. **Outer worker-task cancellation:** cancel the task awaiting evaluate without calling cancelAll; assert producer cancellation, one continuation completion, and subsequent worker reuse.
14. **Late noncooperative worker success:** after cancellation/revision change, release old work that returns a valid evaluation anyway; require no stale publication/cache insertion and preserve the newer evaluation.
15. **Store flush reverse admission without repair:** force old captured revision behind new, reopen immediately after both complete, assert exact latest-admitted state; no final serial flush (P14-3).
16. **Concurrent FIFO complete trace:** record all per-producer sequence markers, validate each ordered trace under concurrent admission, and permit arbitrary cross-producer interleavings (P14-4).
17. **Progress before EOF:** gate enumeration and assert a cumulative loading snapshot before permitting completion; cover threshold crossing, duplicate metadata replacement and exact generation.
18. **100k single-entry batch construction bound:** instrument producer builds/work, require geometric publication rather than per-batch full sorting, and compare the final complete listing independently. Avoid wall-clock pass thresholds.
19. **Cache hit/admission counters:** distinguish root permission checks from enumeration for hit, hidden/sort partition, forced refresh and invalidation (P14-7).
20. **Mac target/discovery acceptance:** on Xcode 16, explicitly build HelmUI and HelmApp after authorized manifest integration, execute both Mac test targets, and assert discovery of native SettingsBindings/ContentNativeAdapter tests and K34 worker tests; a portable-only green run must not satisfy this gate.

  oracle. P8-1/P8-2 are not reopened as current production findings.
- F11 replaced the circular package-size predicate with independent expected
  kinds and exact package speech. Its permissions tests use literal octal
  expectations and both metadata-selection orders. T3PermissionTests' seeded
  oracle still uses production `subject.rawValue`; it is useful arithmetic
  coverage, but the literal K35/F11 cases remain necessary to detect a wrong
  subject-to-bit mapping. No additional permissions defect is claimed.
- T2Store's reducer equivalence checks store delivery against the reducer; it
  cannot establish reducer correctness. T3Navigation supplies independent
  scenario expectations, so the equivalence test is not itself useless.
- T3 checkpoint cancellation tests measure the existing checkpoints, then throw
  at each. This checks propagation, not maximum work between checkpoints. T3's
  snapshot tests check indexes/order at 100k but do not prove linear complexity
  or a Mac UI latency budget. No timing claim is inferred from their pass.
- Accessibility uses injected clocks, calendars and locales rather than ambient
  time for expected speech. Exact French separators/Arabic digits remain ICU
  compatibility assertions to validate on the actual Apple SDK. The worker's
  Date()/current-time-zone input never reaches successful formatting in its
  precancelled test, so it is not evidence of a date-dependent failure there.
- No new unsynchronized access was established in the tested helper locks or
  actor gates. Some gate tests await task results without a separate completion
  watchdog; a continuation regression can hang a run instead of producing a
  bounded failure. Explicit release/cleanup and completion expectations should
  accompany the new lifetime tests.

## Package.swift and scripts/rebuild: Mac Xcode 16 recheck

`Package.swift:1,36–37` correctly selects tools 5.9, Swift 5 language mode and
macOS 14 deployment, without third-party dependencies. `Package.swift:27–35`
still comments out Mac UI/App/executable/test declarations. As P11 already
reported, this is not an app build; uncommenting it wholesale would reference
missing Sources/Helm and omit HelmAppTests. Use the reviewed handoff integration,
including runner exclusions and actual dependencies, then SDK-typecheck the
explicit targets. No new manifest finding is counted.

`scripts/rebuild/run_all.sh:23–26` builds and selects only the six portable
modules. On Mac, `--filter` restricts execution, not compilation; after adding
Mac targets it will not mean that only portable sources compile. The script has
no native UI/App execution gate. `parse_check_ui.sh` parses individual files and
does not typecheck AppKit/SwiftUI, imports, isolation or linking. Both limitations
are disclosed; a green run cannot close Xcode acceptance. The shell constructs
used here are compatible with stock Bash 3.2; Python 3 availability and the
external plan path must be provided on the Mac. Source the Linux env only in the
Linux environment; use Xcode's selected toolchain for native validation.

`check_coverage.py:86–119` consumes Linux-style `Class.method` case names and
labels evidence `linux-tested`. Darwin XCTest's `-[Module.Class method]` form
must be normalized and the evidence platform represented before using Mac logs
to generate a ledger. This is a portability limitation of Linux-labelled tooling,
not evidence that any Mac tests have failed. Keep Mac acceptance separate until
that support exists. Existing report-only citation coverage remains non-semantic.

No Mac SDK is available in this lane. Native monitor callbacks and SwiftUI actor
witnesses remain unverified; no speculative SDK failure is labelled confirmed.
