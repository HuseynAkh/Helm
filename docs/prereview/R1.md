## Findings

### R1-1 — high — quarantine does not prevent already-queued work from starting

**Location:** `Sources/HelmFileSystem/Live/IOExecutor.swift:26`, `:36`, `:42`.

**Scenario:** Use width 1 and timeout 0.6 seconds. A starts and blocks. Enqueue B after 0.25 seconds. A times out; a fresh C request correctly fails with `timedOut`. Release A before B's own deadline. B starts and succeeds on the quarantined volume. The queue lookup checks quarantine only when accepting a request; `state.begin()` checks only that request's completion state. No shared quarantine check protects the transition from queued to running.

**Evidence:** `/tmp/R1-io.swift`, compiled against `/tmp/build-R1` module objects, produced:

```text
first timedOut
fresh admission timedOut
QUEUED BODY STARTED AFTER QUARANTINE
queued result 2
```

The probe's bodies only synchronize/return integers. A real queued mutation could instead alter paths while the user is reconciling an uncertain timed-out mutation. This is an existing quarantine gap exposed by reviewing P2-1, not a claim that wave 10 introduced it. The exact P2-1 cancellation-after-start scenario is repaired.

**Exact fix:** Make quarantine and queued-to-running admission atomic under an executor-owned per-volume state. Mark all not-started requests on that volume failed when quarantine begins, and prevent their bodies from entering. Preserve the real completion behavior for requests already running. Avoid a separate unlocked `isQuarantined` check followed by `begin`, which introduces another race. Test A blocked/B queued/C fresh, and assert B's body is never called after A times out. Include a different-volume control and cancellation-before-install coverage.

**Test sensitivity:** `testCancellationAfterStartRetainsCompletion` and the started-copy executor test correctly fail if the wave-10 cancellation fix is reverted. They do not cover queued work after a timeout, so both pass with this gap.

### R1-2 — medium — cancelled composite tag edits can start a fallback write

**Location:** `Sources/HelmFileSystem/Tags/CompositeTagStorage.swift:20`–24; bulk cancellation guard at `:51`.

**Scenario:** A batch enters `primary.apply`; the task is cancelled while that provider is in progress; primary returns `unsupportedFilesystem` without writing. Composite then starts `fallback.apply` despite cancellation. A cancellation-agnostic fallback writes tags to that item. The outer batch sees success and only stops at the next item. This is a new primitive begun after cancellation, unlike preserving an already-completed write.

**Evidence:** `/tmp/R1-tags.swift` uses a primary that cancels its current task and throws `TagAdapterError.unsupportedFilesystem`, with `InMemoryTagStorage` as fallback. Two URLs are passed through `TagBulkApplier`. Output includes success for `/a` and fallback `TagSet(tags: [FinderTag(rawValue: "red")])`. No real metadata was changed. A suspended primary followed by external task cancellation exercises the same boundary.

**Exact fix:** Check cancellation before starting the primary mutation and, after classifying an unsupported error, immediately before invoking the fallback mutation. Do not check after a successful write in a way that discards its success. Add a gated primary/fallback-spy regression: cancel while primary is suspended, release it with unsupported, require zero fallback calls and cancelled outcomes. Retain ordinary unsupported fallback and permission-denied/no-fallback controls.

**Test sensitivity:** The new Core and filesystem bulk tests correctly detect reverting their loop checks, including cancellation errors and pre-cancelled tasks. None routes cancellation through a Composite unsupported-to-fallback transition. This is a residual P3-2 coverage/safety gap, not a regression in the newly added loop.

### R1-3 — low — UI regression checks use another lane's fixed scratch directory

**Location:** `Tests/HelmUITests/PrereviewTests/F4RegressionTests.swift:14`; `Tests/HelmUITests/PortableRunner/run.py:5`.

**Scenario:** A clean R1 or CI environment builds dependencies in its own scratch directory. The regression test nevertheless invokes `swiftc` with `/tmp/build-F4/debug/Modules`; the runner also builds/links into `/tmp/build-F4`. Without that directory it fails despite correct sources; with stale contents it checks the adapter against a different Core build. This undermines both reproducibility and lane isolation. The active Linux manifest does not execute these UI tests, so the 530-test green result does not catch it.

**Exact fix:** Have the runner accept one explicitly configured scratch/module directory and pass it to the subprocess test through an environment variable. Validate that directory and use it consistently for compilation, linking, and runtime libraries. A missing configuration should give a clear harness error, not silently select another lane's build. Change belongs to the test/script owners, not R1.

**Verification workaround:** Copied the runner and this one test to `/tmp`, replacing only their fixed scratch paths with `/tmp/build-R1` and directing the copied runner to the copied test. No repository test or script was changed. All 50 portable UI/app tests passed against R1 dependencies.

Its planning context also has an empty manifest, so it does not exercise the former per-source full-manifest scan at all. **Exact fix:** Add internal diagnostic counters or injectable comparison/visit seams at the actual planner/journal call sites, and assert work budgets with a nonempty manifest and many unrelated sources. Cover target containment, manifest visits, and duplicate journal insertions separately. Keep timing as diagnostic and preserve the existing functional 100k assertions. This finding concerns regression strength, not an observed current performance failure.

## Concurrency, preservation, and remaining limits

- **IOExecutor/OperationExecutor:** Begin/cancel completion is exactly once under the result lock; cancellation before continuation installation is retained. Started primitives can finish even after cancellation and success is journaled. Timeout still returns before a blocked kernel call completes, so reconciliation is mandatory. R1-1 concerns work that has not yet begun, which can and should be prevented. A successful mutation followed by failed/cancelled metadata lookup can yield a nil token; UndoPlanner refuses unsafe inverses rather than fabricating evidence.
- **Undo mitigation:** Refusing all expected-token directory retirement is deliberately broader than refusing changed descendants. Legacy `Services/UndoService.swift` removed copy/create outputs; the rebuild correctly rejects that destructive model, but unchanged-folder undo is still unavailable. Do not advertise P2-3 as completed F-059 parity. Partial inverse execution before encountering a refused tree remains a user-visible possibility; report actual outcomes.
- **JSONFileStore:** Main-actor dirty/loading guards are before suspension; disk actor's synchronous save plus monotonic revision prevents an older save from replacing a newer revision. Unsupported schema/read failures keep it read-only; corruption recovery backs up original bytes before empty state. No new overwrite defect established. Repeated clean flushes and external editors are not a multi-process synchronization guarantee. The loading-time replace no-op should remain visible in the public API's integration contract.
- **ThumbnailCoordinator:** HEAD's deinit fix addresses ownership release; it does not add bounded producer concurrency. Producer adapters must honor cancellation. K29's concurrent throttle edits were not judged here.
- **Composite tags:** Unsupported-only fallback preserves denied errors; aggregate success must remain success when cancellation arrives after completion. R1-2 asks for cancellation before a distinct fallback attempt, not rollback or relabeling a completed write.
- **Batch rename:** Detached synchronous evaluation already in progress is explicitly allowed to finish in `fixes-F4.md`. Revision checks protect publication, but repeated edits more than 150 ms apart can overlap expensive evaluations, and sheet dismissal does not cancel that pure CPU work. This is a documented resource limitation, not counted as an undisclosed regression. Consider a bounded latest-request worker/cooperative planner before claiming sustained 100k-input responsiveness. Cancelling a detached task alone cannot interrupt the current synchronous planner.
- **Sidebar incidental change:** Legacy `ViewModels/SidebarViewModel.swift:178` considers favorites, bookmarks, devices, Trash, excluding starred. The local fallback restores that policy and retains component-boundary containment. Core's broader policy and leaf-local duplication still need a shared decision; no new defect established.
- **UI detail cache:** Immutable result plus lock-protected one-page cache is coherent; copied models share cache safely. Rebuilding a completed row from scratch loses caching, so the host must retain it. Pagination changes navigation/VoiceOver behavior and needs Mac acceptance.
