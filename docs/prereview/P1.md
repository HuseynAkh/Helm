## Findings, ranked by severity

### P1-1 — high — nested batch rename produces an executable plan with invalid paths

**Location:** `Sources/HelmCore/Naming/BatchRenamePlanner.swift:74`, especially lines 82–87; missing ancestor validation in `assemble` at line 49.

**Problem:** The planner validates duplicate names within each parent, but does not detect a selected source containing another selected source. Its first phase changes the ancestor path while subsequent steps retain that original path. It returns `canExecute == true` for a plan that cannot finish. With the temporary-name strategy, failure can leave the selected folder under a hidden `.helm-rename-*` name unless execution successfully rolls back. This is a partial-mutation risk, not a claim that deletion was observed.

**Concrete scenario:** In an expanded list select `/a/folder` and `/a/folder/child`, then prepend `new-`. Observed steps:

```text
/a/folder -> .helm-rename-1
/a/folder/child -> .helm-rename-2
/a/.helm-rename-1 -> new-folder
/a/folder/.helm-rename-2 -> new-child
```

The second source no longer exists after step one. Reversing input order does not solve the second-phase path problem. The legacy controller (`Controllers/ContentViewController.swift:609`) also stops at the first rename error; the rebuild explicitly promises safe planning for F-055/B-047/P-136, so the old partial-execution behavior is not a safety justification.

**Exact suggested fix:** Before emitting any steps, reject strict ancestor/descendant source pairs using standardized path components and the applicable volume comparison rules. Add an explicit blocking `BatchRenameIssue` for overlapping sources; return no steps and retain previews. Reject only a selected ancestor whose path will actually change, or conservatively reject all such pairs with a clear message. If nested renames are to be supported instead, implement a dependency-aware path-rewriting plan for both phases and rollback; simply sorting by depth is insufficient.

**Missing regression:** `BatchRenameTests.testSwapsHaveSafeTwoPhaseOrdering` simulates a flat dictionary keyed by basename, so it cannot reveal parent-path invalidation. Test both input orders with nested sources and assert refusal before mutation, plus a sibling-folder control case.

### P1-2 — high — drag validation performs quadratic work on the selection

**Location:** `Sources/HelmCore/DragDrop/DropPlanner.swift:18`–22.

**Problem:** The overlap guard compares every path against every other path on every proposal. Ordinary unrelated files take the worst-case `n * (n - 1)` prefix checks. This is synchronous preflight used for cursor feedback; a large selection can stall a drag before any file operation starts. Moving it to a background task alone does not fix the work or repeated drag-update cost.

**Concrete scenario and measurement:** Propose a same-volume move of `/source/file0` through `/source/fileN` to `/target`. Linux debug build, one proposal per size:

| Selected files | Observed elapsed seconds |
| --- | ---: |
| 1,000 | 0.308 |
| 2,000 | 1.245 |
| 4,000 | 5.166 |

These are diagnostic debug measurements, not macOS release benchmarks. Doubling input produces approximately four times the runtime. A 100,000-item selection requires 9,999,900,000 pair comparisons; that count follows directly from the loops and was not timed. F-067 and the architecture's 100k-item interaction goals make this user-visible.

**Exact suggested fix:** Replace the all-pairs overlap scan with a path-component trie (reject a terminal ancestor during insertion and terminal descendants at insertion completion), or sort component arrays lexicographically and check adjacent entries for equality/ancestry. Keep original source order for execution. Cache selection-only validation for a drag session so modifier/target updates do not rebuild it. Preserve component boundaries (`/a` must not overlap `/ab`).

**Missing regression:** `DropPlannerTests.testInvalidAndOverlappingSources` checks only two-item inputs. Add large unrelated selections and ancestor/duplicate permutations against a simple reference on small inputs; benchmark the large case separately instead of asserting a brittle wall-clock threshold.

### P1-3 — medium — changing sort while renaming discards the latest deferred listing

**Location:** `Sources/HelmCore/State/TabReducer.swift:67`; overwrite at `State/TabNavigation.swift:93`.

**Problem:** During inline rename, monitor/load updates correctly go into `deferredSnapshot`. A subsequent `.setSort` sorts the old visible `snapshot` and passes it to `publish`, which overwrites that newer deferred snapshot. `.endInlineRename` then publishes stale contents. A newly created file disappears from the display, or a deleted entry reappears, until another refresh/event occurs.

**Concrete scenario:** Display `/a/one`; select it and begin inline rename. Receive a monitor snapshot containing `one` and newly created `new`. Change sort to descending; end rename. Reproduced final names: `["one"]`; expected `["one", "new"]` in descending order. Sorting through a menu or applying view options need not end field editing first, and the reducer does not enforce that assumption.

**Exact suggested fix:** In the non-search `.setSort` branch, resort `next.deferredSnapshot ?? next.snapshot` and pass that result to `publish`. Retain the existing deferred-publication rule while editing. Audit other metadata-only republish paths (e.g. monitor-unavailable failure) so they also preserve the most recent deferred contents instead of restamping the old visible array.

**Missing regression:** `TabReducerTests.testInlineRenameDefersSnapshotAndSelectionRemoval` tests deferral alone, while `testSortDuringLoadAndHiddenCompletionInvalidation` tests sorting alone. Add monitor-add and monitor-remove snapshots followed by sort during rename, then end editing and assert exact entries as well as sort.

### P1-4 — medium — column load acceptance cannot distinguish old and new requests for the same folder

**Location:** `Sources/HelmCore/Content/ColumnBrowserState.swift:43`–48; `ColumnNavigation.load` at line 18.

**Problem:** `push` authenticates a response only by column index, current selected directory ID, and destination path. No request generation is represented. Selecting A, then B, then A makes an old A response valid again. A late callback can overwrite a fresh column and truncate its descendants. Cancellation alone is insufficient for a provider that completes after cancellation; this is the same stale-publication class the tab reducer otherwise handles explicitly (B-009/P-080).

**Concrete scenario:** Select `/a/folder` and start load A1; select `/a/other`; select `/a/folder` and start A2. Deliver A2 with child `new`, then A1 with child `old`. Both `push` calls return true and the final column contains `old`. This was reproduced with public APIs. The same hole exists after reloading an ancestor while preserving its selected path.

**Exact suggested fix:** Give each column navigation request a generation/token, include it in `ColumnNavigation.load`, and require it in `push`. Advance/invalidate it when selection changes, ancestor snapshots are replaced, columns are popped/truncated, or a newer load starts. Match the owning column identity as well as the token so a reused numeric column index is not sufficient. The adapter should cancel old tasks too, but acceptance must reject their callbacks independently.

**Missing regression:** `ColumnBrowserStateTests.testAncestorChangeTruncatesAndRejectsStalePush` stops at A→B. Extend to A→B→A with replies reversed and verify that the stale push returns false and preserves fresh contents/descendants.

### P1-5 — medium — restarting a partial Back load destroys pending selection restoration

**Location:** `Sources/HelmCore/State/TabNavigation.swift:20`; callers `.refresh` and hidden-setting restart in `State/TabReducer.swift`.

**Problem:** `startLoad` unconditionally replaces `restorationIDs` with the currently visible selection. During streaming Back/Forward restoration, the selected item may not yet be in the first batch, so visible selection is empty while `restorationIDs` correctly retains its ID. Refreshing or restarting for hidden-file settings throws that retained ID away, even when the replacement full listing contains the item.

**Concrete scenario:** Back history for `/a` contains selection `/a/two`. Go Back, accept a first batch containing only `/a/one`, then send `.refresh`. Finish the replacement load with both `one` and `two`. Reproduced selection is empty; expected `/a/two`. This violates F-005/B-011 selection restoration without any new selection intent from the user.

**Exact suggested fix:** Preserve an existing restoration set when restarting the same committed location: assign `state.restorationIDs = state.restorationIDs ?? (state.search == nil ? state.selection : state.underlyingSelection)`. Keep clearing it on explicit selection changes and terminal completion/failure as appropriate; do not carry it across a different navigation target. Test refresh and hidden-setting restart after the first Back/Forward batch.

**Missing regression:** `TabReducerTests.testHistoryRestorationWaitsForLaterBatch` tests uninterrupted loading only. Its first-batch/second-batch fixture is ideal for inserting `.refresh` or `.toggleHidden` between those batches.

```swift
import Foundation
import HelmCore
func u(_ p: String) -> URL { URL(fileURLWithPath: p) }
let loc = Location.directory(u("/a"))
let context = ReducerContext(now: .distantPast, homeDirectory: u("/home"))
func e(_ p: String) -> FileEntry { FileEntry(url: u(p)) }
func snap(_ entries: [FileEntry]) -> PresentationSnapshot {
    SnapshotBuilder.build(location: loc, entries: entries)
}
func send(_ action: TabAction, _ state: inout TabState) {
    state = TabReducer.reduce(state, action, context: context).0
}
var state = TabState(location: loc, homeDirectory: u("/home"))
send(.refresh, &state)
send(.loadFinished(state.loadGeneration, snap([e("/a/one")])), &state)
send(.setSelection([e("/a/one").id], source: .user), &state)
send(.beginInlineRename(e("/a/one").id), &state)
send(.monitorSnapshot(state.monitorGeneration,
    snap([e("/a/one"), e("/a/new")])), &state)
send(.setSort(ItemSort(ascending: false)), &state)
send(.endInlineRename, &state)
print("Deferred monitor then sort:", state.snapshot.sortedEntries.map(\.name))

let history = NavigationHistory(back: [
    .init(location: loc, selection: [e("/a/two").id])
])
state = TabState(location: .recent, homeDirectory: u("/home"), history: history)
send(.goBack, &state)
send(.loadProgress(state.loadGeneration, snap([e("/a/one")])), &state)
send(.refresh, &state)
send(.loadFinished(state.loadGeneration,
    snap([e("/a/one"), e("/a/two")])), &state)
print("Refresh during Back selection:", state.selection)

let folder = FileEntry(url: u("/a/folder"), kind: .directory)
let other = FileEntry(url: u("/a/other"), kind: .directory)
var columns = ColumnBrowserState(root: snap([folder, other]))
_ = columns.select(folder.id, in: 0)
let stale = PresentationSnapshot(location: .directory(folder.url),
    sortedEntries: [e("/a/folder/old")])
_ = columns.select(other.id, in: 0)
_ = columns.select(folder.id, in: 0)
let fresh = PresentationSnapshot(location: .directory(folder.url),
    sortedEntries: [e("/a/folder/new")])
_ = columns.push(fresh, from: 0, directory: folder.id)
let accepted = columns.push(stale, from: 0, directory: folder.id)
print("ABA stale accepted:", accepted,
    columns.columns.last?.snapshot.sortedEntries.map(\.name) ?? [])

let plan = BatchRenamePlanner.plan(
    items: [u("/a/folder"), u("/a/folder/child")],
    rule: .addText(prepend: "new-", append: ""))
print("Nested plan executable:", plan.canExecute)
for step in plan.steps { print(step.source.path, "->", step.newName.value) }

for count in [1000, 2000, 4000] {
    let sources = (0..<count).map {
        DraggedItem(url: u("/source/file\($0)"), volumeID: "v")
    }
    let start = Date()
    let result = DropPlanner.proposal(sources: sources,
        destination: DropDestination(location: .directory(u("/target")), volumeID: "v"))
    print("Drop", count, Date().timeIntervalSince(start), result.operation as Any)
}
```
