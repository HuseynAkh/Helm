## Findings, ranked by severity

### P2-1 — high — cancellation releases the mutation lane while the kernel operation continues

**Location:** `Sources/HelmFileSystem/Live/IOExecutor.swift:35–44`; `Sources/HelmOperations/Execute/OperationExecutor.swift:61–70`.

`onCancel` completes the continuation immediately even after `body()` has begun. The blocking operation keeps running. Unlike timeout, cancellation neither quarantines the volume nor the operation executor. Once cancellation wins `IOResultState.complete`, the later timeout cannot quarantine it either. The operation executor marks the outcome uncertain, but clears `running` and accepts another plan. This is distinct from the documented lack of byte-level cancellation: it exposes overlapping mutations after a supposedly completed cancellation.

**Failing scenario:** start a slow copy/move on a mounted disk, wait until its native call has started, then cancel. `execute` returns `.cancelled`; immediately execute another operation touching the same source/output using the same executor. The second plan is accepted while the first call can still rename/copy/trash those paths. A cancelled Trash can complete without its resulting URL ever reaching origin recording. The existing cancellation test cancels immediately and never asserts that the blocking body has started or tests a subsequent mutation.

**Exact suggested fix:** distinguish queued, running, and completed I/O under the result-state lock. Cancel queued work without starting it. For an already-running mutation, either await its real result and journal that completed primitive before stopping subsequent steps, or return a typed “mutation still in flight” outcome and quarantine every involved mutation lane until that specific body completes and is reconciled. Do not discard late mutation completion/origin information. Test with a deterministic start gate, cancellation after the gate, a second execute, and a completion gate.

### P2-2 — high — failed exclusive writes can permanently unlink another writer's replacement

**Location:** `Sources/HelmFileSystem/Live/LiveFileSystem.swift:137–161`, especially `unlink(url.path)` at line 160.

`O_EXCL` establishes ownership only when the descriptor is opened. Error cleanup later unlinks whatever currently occupies the pathname; it does not establish that it is still the opened file. This is permanent deletion, outside the executor's conservative Trash recovery scheme.

**Failing scenario:** a large exclusive write to `new.dat` is in progress. Another process renames that file away and puts its own valuable file at `new.dat`. The original open descriptor remains valid, but a subsequent write fails (for example ENOSPC). Cleanup unlinks the other process's file. This requires no symlink ancestor and survives all executor path guards.

**Exact suggested fix:** remove pathname-based automatic unlink on failure and retain/report the partial artifact for reconciliation. If automatic cleanup is required later, implement it through an ownership-preserving native mutation design; a separate `lstat`/inode comparison followed by `unlink` still has a race. Add a syscall-injected regression that replaces the pathname between successful open and injected write failure, asserting replacement bytes remain.

### P2-3 — high — undo silently trashes edited descendants because only the directory's token is checked

**Location:** `Sources/HelmOperations/Undo/UndoPlanner.swift:14–18,29–30`; `Sources/HelmOperations/Execute/OperationExecutor.swift:50–52`; `Sources/HelmFileSystem/Live/MetadataReader.swift:38–45`.

The journal captures one token for a whole-tree copy's root. Undo checks only that root before trashing the entire tree. Editing the contents of an existing descendant does not update the ancestor directory's modification time or size. `MetadataReader` also never populates `childCount`; even adding that field would not detect in-place descendant edits. P-074/architecture undo semantics require warning about changed content.

**Failing scenario:** copy `Project` containing `sub/report.txt`; edit and save the existing `report.txt` in place, with no root-directory entry changes; undo the copy. The root token is unchanged, so undo succeeds and trashes the user's edited document without a changed-content warning. Trash retains recovery data, but the promised change protection is bypassed. The existing changed-output test changes a top-level file, not a descendant.

**Exact suggested fix:** journal a complete, strict no-follow post-copy manifest of output descendants and compare it before inverse tree retirement; changed or incompletely readable trees must require explicit confirmation/reconciliation. Include object identity and appropriate content-change evidence. Add a live temporary-directory test that changes only an existing nested file and confirms automatic undo is refused. Do not treat a root child count as sufficient.

### P2-4 — high — undo's expected-token checks become stale before later steps execute

**Location:** `Sources/HelmOperations/Execute/OperationExecutor.swift:30–48`; `Sources/HelmOperations/Undo/UndoPlanner.swift:42`.

Every `expectedTokens` entry is checked once, before the entire sequence. Subsequent awaited progress callbacks, metadata queries and earlier mutations can take arbitrarily long. No token is checked again at the step that will trash/move the relevant output. This is a potentially minutes-long validation gap, not just the acknowledged narrow native stat/rename race.

**Failing scenario:** undo a batch of copies. All destination tokens pass the initial loop. While the first inverse step is slow, another application edits a later output. The later inverse step trashes that newly edited file using the old authorization. A deterministic regression can edit the later item inside its progress callback: that callback runs after the global checks and before `perform`.

**Exact suggested fix:** retain expected identity/token preconditions per inverse primitive and validate immediately before that primitive, after progress callbacks. Update the expected path/identity mapping after successful internal moves so staged renames and swaps remain undoable. Ultimately perform compare-and-mutate through the native coordinated seam; until then, fail closed on mismatches and explicitly retain the residual native race limitation. Test a change during an earlier step, not only before calling `execute`.

### P2-5 — high — Replace can move the selected source itself into Trash during a Copy

**Location:** `Sources/HelmOperations/Plan/OperationPlanner.swift:73–80,125–128,145–155`.

Overlap validation excludes the current source when checking replacement targets. It rejects a target inside the source, but permits the opposite relation: the replacement target can be an ancestor containing that source. Replacement then moves that ancestor to backup and trashes it, taking the selected source with it. This is not the documented folder-replace/no-merge choice: a Copy unexpectedly removes its own source pathname.

**Failing scenario:** source directory `/dest/A/sub/A`, destination directory `/dest`, policy `.replace`. The existing target is `/dest/A`. The executable plan copies the nested A to `/dest/.helm-stage-A`, moves `/dest/A` to backup, installs the stage and trashes the backup. Copy reports success although `/dest/A/sub/A` is gone and the original selected item is inside the trashed backup. For Move, its final source-retirement verification fails only after these mutations.

**Exact suggested fix:** before emitting replacement steps, reject a target equal to or an ancestor of **any** selected source, including the source currently being planned; use component-boundary and filesystem case semantics. Keep ordinary keep-both copies to ancestors valid. Add separate Copy/Move Replace regressions asserting a blocking issue and zero steps for this scenario.

### P2-6 — medium — mutation preflight and verification accept incomplete directory listings as complete

**Location:** `Sources/HelmFileSystem/Live/LiveFileSystem.swift:60–62`; `Sources/HelmFileSystem/Protocol/FileSystem.swift:85–90`; `Sources/HelmOperations/Plan/PlanningContext.swift:47–54`; `Sources/HelmOperations/Execute/TreeCopyVerifier.swift:25–32`.

Live enumeration skips every per-entry metadata failure, with only an out-of-band diagnostic whose default implementation is empty. The stream finishes successfully. The same permissive stream is used for collision names, the source manifest, and verification. Callers therefore cannot distinguish an empty directory from a directory whose children all failed metadata reads. A UI partial listing policy has leaked into safety-critical “complete” snapshots.

**Failing scenario:** a provider/network metadata error consistently hides source child `secret` during planning and verification. A copied output lacking `secret` compares equal because both visible tree dictionaries omit that entry. The verifier can authorize retirement despite never proving completeness. Independently, `childNames` returns a set missing existing entries, violating the executor comment that it rechecks complete names (exclusive primitives mitigate overwrite but do not repair the false snapshot).

**Exact suggested fix:** add a strict enumeration mode or separate strict name/manifest API that throws on any child failure and never returns a successful incomplete snapshot. Use strict mode in context construction, verification and collision preflight; reserve partial metadata listings for UI use with an explicit warning. Test an enumeration adapter that returns an entry-read failure and verify that no retirement plan proceeds. This is separate from the documented size-only verification limitation.

### P2-7 — medium — selecting 100k files triggers billions of synchronous comparisons

**Location:** `Sources/HelmOperations/Plan/OperationPlanner.swift:62–80,96–101`; `Sources/HelmOperations/Journal/OperationJournal.swift:23–26`.

Source validation compares every pair, repeatedly standardizing and case-normalizing paths. Transfer target validation scans all sources again per source. Space estimation filters the complete manifest for each item. Journal recording scans every preceding outcome for duplicate step IDs. These are independent quadratic passes before/during ordinary large-selection operations; the pure planning loops cannot honor cancellation while running.

**Failing scenario:** select 100,000 sibling files and copy/move them to another directory. `validateSources` alone performs 4,999,950,000 pair comparisons, before the next full-selection scan. A successful 100k-step execution then performs approximately the same number of journal membership comparisons. Existing small randomized operation tests do not exercise this scale; listing 100k files is not an operation-planning test.

**Exact suggested fix:** normalize source paths once; detect ancestor/duplicate selections using a sorted component representation or trie, index source containment for target checks, and precompute manifest byte totals by source root. Maintain a per-journal-entry `Set<StepID>` alongside ordered outcomes. Add an operation-planning scale benchmark and deterministic comparison-count test, plus a 100k-outcome journal test; avoid fragile millisecond timing assertions.

### P2-8 — medium — ordinary tar archives containing a root `./` member are rejected

**Location:** `Sources/HelmFileSystem/Archive/ArchiveSafety.swift:46–47`; `Sources/HelmFileSystem/Archive/ArchivePlanner.swift:71`.

Path normalization turns the conventional directory member `./` (or `.`) into the empty string and unconditionally rejects it. A tar created from the contents of a directory commonly includes that root directory entry. The advertised tar/tgz extraction planner therefore rejects a safe and routine archive before a confined runner can execute it.

**Failing scenario / text-only regression:** call `ArchiveSafety.validate` with `[ArchiveMember(path: "./", kind: .directory, expandedBytes: 0, compressedBytes: 0), ArchiveMember(path: "./notes.txt", expandedBytes: 1, compressedBytes: 1)]`. It throws `.unsafeMember("./")`. Feed those same inspected members to `uncompress` for `notes.tar`: planning also fails.

**Exact suggested fix:** explicitly accept and ignore a normalized root directory marker after rejecting absolute paths, traversal and unsafe member kinds. Continue rejecting empty raw names and root markers declared as files; keep member-count/runtime budgets. Add `.` and `./` directory-marker tests plus negative file-marker/traversal cases. The confined extraction adapter must not apply root-marker metadata in a way that escapes or disables the staging policy.

## Coverage limits and needed changes elsewhere

- The documented conservative deviations—source retirement to Trash, no directory merge, no durable journal yet, no byte cancellation/progress, refusal of symlink ancestors, and tree kind/size verification rather than content hashes—are not counted as additional defects. Size-only verification and source-retirement TOCTOU remain important Opus integration decisions; a successful copy of equal-sized but different bytes is not content proof.
- `Monitor`, `Providers`, `Tags`, `Virtual`, `Volumes`, fake adapters and clipboard code were inspected. No additional proven high-severity issue is asserted there. Synchronous xattr calls under the shared tag mutation lock on a stalled mount deserve native I/O scheduling review. Darwin resource-value behavior for dangling symlinks, FSEvents context lifetime/CF bridging, native Trash identities and provider metadata need macOS fixtures; Linux success does not verify them.
- Existing replacement/adversarial tests meaningfully check path presence and sizes, but do not prove byte preservation: for example `K15ReplacementBoundaryTests.swift:46–59` accepts any retained files of lengths 2 and 3. Add byte-content assertions through a test-only reader or live temporary fixtures when implementing the fixes. Do not use size conservation as evidence of payload fidelity.
- Strong object identity/content evidence may require a HelmCore/FileSystem contract addition owned by other lanes. P2 has made no such change. Opus should coordinate those owners rather than patching contracts in a read-only review lane.
