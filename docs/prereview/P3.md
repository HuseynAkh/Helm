## Findings, ranked by severity

### P3-1 — high — Failed existence checks can turn existing user data into an empty writable store

**Location:** `Sources/HelmPersistence/JSONFileStore.swift:10`, with writable state enabled at line 54.

**Defect:** `fileExists(atPath:) == false` is treated as proof that the document does not exist. That Boolean also covers failures to determine existence, including inaccessible ancestors. The store then successfully loads an empty payload and permits replacement, bypassing both the corruption backup and unsupported-version protections. This undermines the B-029 preservation requirement.

**Failing scenario:** An existing `stars.json` is behind an ancestor whose traversal permission is temporarily denied. Launch loads an empty store without an error. Restore access, add a star, then flush: the old document is atomically overwritten with only the new star. A temporarily inaccessible future-version document is vulnerable in the same way. Established by source/API semantics; not reproduced under this privileged Linux account.

**Exact suggested fix:** Attempt `Data(contentsOf:)` directly. Return the empty payload only for a positively identified missing-file error; propagate permission, I/O, and other failures so `writable` remains false. Add an injected read-error seam or an unprivileged fixture testing EACCES separately from ENOENT, and verify that restoring access cannot cause the failed-load instance to overwrite the document.

### P3-2 — high — Cancelled tag batches continue mutating remaining files

**Location:** `Sources/HelmCore/Presentation/TagStorage.swift:34–40`.

**Defect:** The aggregate mutation loop never checks cancellation, and its catch-all treats `CancellationError` as an ordinary per-item error before proceeding. A conforming storage implementation need not check cancellation; the actual xattr writer is synchronous inside its actor. Cancelling a batch therefore does not stop subsequent metadata writes.

**Failing scenario:** Begin tagging 100,000 selected files, then cancel after the first write. Remaining files continue to receive the tag. Even a task cancelled before entering the aggregate edits its first item: a Linux probe using `InMemoryTagStorage` returned one successful mutation from an already-cancelled task.

**Exact suggested fix:** Check `Task.isCancelled` before every storage call, stop on `CancellationError`, retain completed outcomes, and report unattempted items as cancelled (or add an explicit cancelled/unattempted result field). Do not claim an already-completed write was rolled back. Test pre-cancelled calls and cancellation while the first storage call is suspended, asserting that the second item is never passed to storage.

### P3-3 — medium — Reload silently discards an unflushed edit

**Location:** `Sources/HelmPersistence/JSONFileStore.swift:49–55`, debounce at lines 62–65.

**Defect:** The revision check detects only edits made *during* the awaited load. It does not detect an existing dirty revision when load begins. Loading an older disk payload replaces current items while leaving the pending debounce associated with the same revision; that debounce can then save the stale payload. A concurrent edit during reload also disables writing on the existing store via the catch at line 55 rather than preserving a usable dirty state.

**Failing scenario:** Load, replace with `[1]`, flush, replace with `[2]`, immediately load again. Items become `[1]`, with no error. A subsequent flush persists `[1]`. Reproduced on Linux. Current wrappers generally load only during initialization, so this is a public-store lifecycle defect rather than a demonstrated existing UI call path.

**Exact suggested fix:** Track a successfully persisted revision and reject reload when the current revision is dirty, before disk I/O; alternatively provide an explicit flush-then-reload operation. Use a loading state to reject concurrent replace/reload operations without disabling an otherwise valid store. Add a test for dirty-before-load, distinct from dirty-during-load, and assert the pending edit remains available.

### P3-4 — medium — Thumbnail producers outlive a released coordinator

**Location:** `Sources/HelmCore/Imaging/ThumbnailCoordinator.swift:49–60` and the absence of teardown for `flights`.

**Defect:** Each producer runs in an unstructured task that captures the producer strongly and the coordinator weakly. Releasing the coordinator releases task handles but does not cancel those tasks. There is no shutdown/deinitialization path cancelling all flights or finishing their subscribers. The documented requirement that producers cooperate with cancellation cannot help when cancellation is never sent.

**Failing scenario:** A window-scoped coordinator starts a cancellation-aware slow thumbnail generator. Close the owner without cancelling every individual token. The coordinator can disappear while its generator continues reading/rendering until completion; repeated window creation/closure accumulates orphaned work. Established by source inspection. Existing tests cover token/consumer cancellation, not owner teardown.

**Exact suggested fix:** Add deterministic shutdown that removes all flights, cancels every task and finishes every continuation, and require the owner to await it before release. Also implement a Swift-5-compatible synchronous deinitialization safety net for the stored task/continuation handles (no task capturing `self` from deinit). Test that dropping the final coordinator reference cancels a suspended producer and terminates its subscriber stream.

### P3-5 — medium — Typed extension rows accept a spelling that can never match

**Location:** `Sources/HelmSearch/Query/SearchQueryParser.swift:27–34`, compared with lines 50–52; `Sources/HelmCore/Search/SearchSpecification.swift:41`.

**Defect:** Typed `.ext` filters validate a dot-trimmed value but keep the original value in `clauses`. Text tokens store the trimmed value. Thus the criteria editor and toolbar text compile equivalent user input differently, contrary to their shared-filter contract (F-043/F-044).

**Failing scenario:** A criteria row `.fileExtension(".txt")` produces `.ext(".txt")`; `report.txt` has path extension `txt`, so it never matches. The token `ext:.txt` matches the same file. Linux probe output was `extension typed/token: false true`. Existing row tests use only `txt`.

**Exact suggested fix:** Normalize extension literals once in the common compile path for both typed filters and parsed tokens, validate the normalized value, and emit `.ext(normalized)`. Keep the editor's original text if needed, but use normalized predicate data. Test dotted/undotted and uppercase extensions across both inputs, plus dot-only rejection.

### P3-6 — medium — Saved-search encoder can produce documents its decoder refuses

**Location:** `Sources/HelmSearch/SavedSearch/SavedSearchDocument.swift:16–23`.

**Defect:** Decode enforces a 1,048,576-byte document limit, but encode only validates the query and imposes no serialized-size limit. The permitted filter bounds already exceed the document limit after JSON overhead; the unbounded document name makes the mismatch even easier to reach. A successful save can therefore become an unreadable saved search on reopening (M23).

**Failing scenario:** Encode a document with empty text and 256 `.name` clauses, each containing 4,096 ASCII `a` characters. All clauses pass parser validation. The Linux probe successfully encoded 1,053,544 bytes, then immediately failed to decode those exact bytes with `SavedSearchError.malformed`. No disk save is needed to reproduce. Seeded round-trip tests use small strings and miss this boundary.

**Exact suggested fix:** Share a maximum-document-byte constant, encode to a local `Data`, and reject oversized data before returning it to a caller that may save it. Apply the same output-size invariant to newly constructed/replaced Finder documents, whose decoder has the same limit. Add round-trip tests at the byte boundary, including escaped JSON text and large names; oversized input must fail before a caller replaces an existing saved document.

### P3-7 — medium — Original enumeration API enters explicitly supplied package/symlink roots

**Location:** `Sources/HelmSearch/Fallback/EnumerationSearchService.swift:31–34`.

**Defect:** The public fallback service prunes package/symlink *children*, but enumerates pending roots without inspecting their kind. Its documented no-package/no-symlink traversal guarantee therefore does not hold for `.currentFolder`, computer roots, or Trash roots. The newer `SearchEngine` explicitly checks `entry(at:)` before enumerating, so callers get different policy depending on which public API they use. The README documents preserved throwing-permission behavior for the old API, but does not document this traversal exception.

**Failing scenario:** Search with `.currentFolder(/Applications/Tool.app)` using the original service. Its internal files are returned even with default package-skipping policy; the newer engine returns no entries. Likewise a root `/search/link` pointing to an external directory is passed directly to filesystem enumeration, which can traverse its target. Existing fallback tests exercise hidden descendants and duplicate roots, while package/symlink-root tests exist only for `SearchEngine`.

**Exact suggested fix:** Inspect each pending root with `fileSystem.entry(at:)` and enumerate only actual directories, excluding package and symlink kinds. Prefer sharing the checked traversal implementation with `SearchEngine` while deliberately retaining the older API's error policy. Add a spy filesystem test asserting that `enumerate` is never called for explicit package or symlink roots.
