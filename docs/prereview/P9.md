## Findings, ranked by impact

### P9-1 — Medium — validation and ordinary reload can publish in reverse freshness order

**Locations:** `Sources/HelmCore/Store/WindowStore.swift:130` (separate validation/reload cancellation slots); `Sources/HelmFileSystem/Loading/DirectoryEffectRunner.swift:68–83`; `Sources/HelmCore/State/TabReducer.swift:45–53`.

**Wrong:** Validation replaces only another validation; refreshPaths replaces only another reload. Both emit snapshots with the same monitor generation. The coalescer revision protects a validation acknowledgement against a newer root event, but does not identify an ordinary reload or order its result against validation. Either class of result can overwrite the other, including overwriting a validation failure with an obsolete ready snapshot.

**Concrete failing scenario:** A rescan starts reload R and captures the old `/a` contents, then suspends before returning. A root-change event starts validation V; `/a` now contains a different listing. V completes and publishes the new snapshot. R completes afterward, still uncancelled and carrying the same watch generation/location. The reducer accepts it and restores the old contents. Alternatively V fails because the root disappeared, and R subsequently erases that failure with its old successful snapshot. No foreground refresh or generation change is needed.

**Exact fix:** Give all snapshot-producing monitor work for a tab one shared monotonically advancing request identity, in addition to watch generation. Validation/root invalidation retires prior refresh work; ordinary refresh must preserve pending root-validation priority. Carry the identity in both success and failure actions and reject retired replies at reducer admission, including already queued replies. Cancel superseded tasks as a resource measure, without relying on cancellation alone. Coordinate the public action changes with the Core owner.

**Coverage gap / relationship to earlier fixes:** F6 repairs foreground-load versus monitor ordering; K34 tests validation revision acknowledgement and cancellation on refresh/shutdown. Neither tests concurrent validation and ordinary reload within one watch generation. Add a gated R→V→V-result→R-result test, with both successful and failed V, asserting final entries/phase. This is a remaining K34 integration gap, not a repetition of P5-1's retired foreground epoch.

### P9-2 — Medium — failed staged navigation still loses changes to the retained directory

**Locations:** `Sources/HelmCore/State/TabNavigation.swift:7`; `Sources/HelmCore/State/TabReducer.swift:49–55`, `:38–44`.

**Wrong:** Staging a different target immediately clears `monitorDirty`, while the committed location and old watcher remain active until commit. Both monitor-event and monitor-snapshot guards then discard everything while `pendingNavigation != nil`, before dirty tracking can run. On a pre-commit load failure the old location is retained, but replay has no remembered invalidation.

**Concrete failing scenario:** Display `/a/x`; navigate to a slow or inaccessible `/b`. Before any `/b` batch commits, delete `/a/x` externally and deliver the current `/a` watch's rescan. It is ignored. `/b` fails permission checking; the reducer keeps `/a` and its old snapshot containing `x`, emits no refreshPaths, and never repairs the stale listing unless another event or manual refresh arrives. A previously recorded dirty flag is also lost when staging `/b`, even if `/b` never commits.

**Exact fix:** Retain invalidation state for the committed location until navigation actually commits. During pending navigation, record matching old-watch changes without publishing old snapshots or refreshing the target. On pre-commit failure, replay one reconciliation of the retained location; on successful commit, retire the old dirty state with the old watch. If root-validation events are retained separately, preserve their priority over ordinary dirtiness. Keep rejected generations rejected.

**Coverage gap / relationship to earlier fixes:** This is an incomplete P5-2/F6 repair. `F6StateTests.testDirtyStateRetiresOnDifferentNavigationAndWaitsForActivation` covers successful different-location commit, while the terminal-failure tests cover same-location refresh. Neither covers a failed different-location attempt. Add failure before the first batch, both with an already-dirty old location and with a change received during staging; assert exactly one old-location reconciliation and unchanged history.

### P9-3 — Medium — monitor startup failure leaves a permanently stopped watch registered

**Locations:** `Sources/HelmFileSystem/Loading/DirectoryEffectRunner.swift:29–48`, `:57–59`, `:73–74`; `Sources/HelmFileSystem/Loading/DirectoryReloadCoalescer.swift:46–47`.

**Wrong:** The watch record is installed before `monitor.start()`. If startup throws, the task sends unavailable, finishes the coalescer, stops the monitor and exits, but leaves that record in `watches`. The reducer's unavailable recovery requests validation against the stopped record. A successful directory read cannot acknowledge a stopped coalescer, so its result is silently discarded. There is no monitor replacement or retry effect.

**Concrete failing scenario:** Startup encounters transient permission denial or a temporarily unavailable volume. The unavailable action is delivered after the task has finished its cleanup. Access recovers before the resulting validation read, which succeeds. `acknowledgeRootValidation` returns false because `stopped` is true; no ready action is sent and no live watcher exists. Later file changes cannot trigger recovery. Manual foreground refresh or tab switching can recreate the watch, but the adapter's automatic validation path cannot.

**Exact fix:** Track startup/termination status explicitly and retire the matching watch record on terminal failure. Report watcher failure through a reducer action that can request bounded replacement/retry with a new watch generation once root validation succeeds. Do not reuse a finished coalescer/monitor or clear errors while no watcher is active. Ensure terminal finite-source completion also updates watch ownership. Separately verify that successful root replacement validation recreates native watches where necessary, especially vnode watches tied to the old object.

**Coverage gap:** K34's failed-validation test exercises a missing root while the fake monitor starts successfully; it does not make `DirectoryMonitor.start()` throw and recover. Add a monitor factory that fails its first startup, then succeeds; gate root recovery after cleanup, assert a fresh monitor/coalescer is started, and verify a subsequent change reaches the reducer. This is adapter lifecycle recovery beyond F6's repaired coalescer event precedence.

### P9-4 — Medium — reactivating a clean tab does not reconcile changes made while unwatched

**Locations:** `Sources/HelmCore/State/TabReducer.swift:114–123`; `Sources/HelmCore/State/TabNavigation.swift:86–89`; `Sources/HelmFileSystem/Monitor/PollingMonitor.swift:31–34`; `Sources/HelmFileSystem/Monitor/FSEventsMonitor.swift:88–89` (stream creation).

**Wrong:** Deactivation stops monitoring without marking the listing dirty. Activation starts a new watch and invokes replayMonitor, but that helper does nothing unless dirtiness was already recorded. Starting a new monitor does not imply an initial rescan: polling establishes a fresh baseline, while native FSEvents starts from now. Changes made while the tab was inactive are therefore absent from both the old snapshot and the new watch's event history.

**Concrete failing scenario:** Tab A displays `/a/old` with `monitorDirty == false`. Switch to B, delete `old` and create `new` in `/a`, then return to A without any further filesystem writes. The new polling baseline already contains `new`; it emits no difference. A indefinitely displays `old`. This violates the architecture section 6.4 requirement to restart with a rescan on activation (B-013).

**Exact fix:** Mark the committed listing dirty when monitoring is retired for inactivity, or unconditionally request one reconciliation after installing the activation watch. Preserve that request through an ongoing foreground load and pending navigation, so it runs after the relevant terminal action without overriding a different committed target. Keep watch startup before reconciliation to avoid a new observation gap.

**Coverage gap:** The F6 activation test seeds monitorDirty before deactivation, so it passes despite this defect. Add the ordinary clean-tab sequence with a real reducer/store plus fake monitor baseline; assert an activation refresh effect and the resulting new IDs without injecting an artificial post-activation event.

### P9-5 — Medium — every monitor reload repeats snapshot sorting/indexing on MainActor

**Locations:** `Sources/HelmFileSystem/Loading/DirectoryEffectRunner.swift:7`, `:68`, `:77`; `Sources/HelmCore/State/SnapshotBuilder.swift:7–20`.

**Wrong:** The adapter is MainActor-isolated and its `Task {}` inherits that isolation. `DirectoryLoader.snapshot` sorts off that actor, but after awaiting it the adapter calls synchronous `SnapshotBuilder.build` on MainActor. That sorts the same entries again and constructs the full snapshot indexes. The cancellation check immediately before it cannot interrupt the synchronous sort/index work or let a queued tab-close action run.

**Concrete failing scenario:** Watch a 100,000-entry directory receiving regular changes. Each completed monitor reload performs full natural-order sorting and snapshot allocation on the UI actor, blocking input/window-close handling for that work. The source establishes actor placement and duplicate work; no macOS frame-time or duration measurement is claimed. This is distinct from the previously disclosed synchronous reducer resort when the user changes sort.

**Exact fix:** Materialize the complete immutable PresentationSnapshot in a non-MainActor async worker, with one sorting pass, before returning to the adapter. Retain/forward cancellation to that worker, bound replacement work, and check its request identity immediately before dispatching its result. Avoid introducing an unowned detached task merely to move the CPU work. If already sorted values are accepted, use an explicitly sorted-input construction path rather than calling build again.

**Coverage gap:** K34 adapter tests use one child and assert contents/cancellation before work starts. They pass with this actor violation. Add a worker-isolation assertion or injected build seam proving snapshot construction does not run on MainActor, plus a gated supersession/close test; profile a 100k directory on macOS. Do not use an unstable Linux wall-clock threshold as proof of responsiveness.

## Persistence review and limits

No additional confirmed corruption/overwrite defect was established in the reviewed persistence paths under their documented one-instance-per-document and migration-before-store-construction contracts. F3's definite-missing-file classification and dirty/loading guard remain in place. JSONDisk and PreferenceDocumentFile serialize synchronous atomic saves and reject stale revisions. Atomic replacement is not a multi-process transaction or a claimed power-loss durability guarantee.

Tag catalogue v0 migration preserves raw tag strings before normalization; failed/unknown envelope reads do not authorize saving. Corrupt tag/view-option documents retain original bytes plus a backup and expose read-only defaults. Nested unknown view-option versions also enter that conservative recovery path. Explicit flush failures retain in-memory edits. K34's 96-pixel folder default is shared for construction/decoding/nonfinite input; explicit overrides and the separate global slider range remain intact. No demand to adopt the old PreferencesView's differing 64-pixel fallback is made.

Migration's pre-load sequencing, shared-store ownership, explicit quit flush, recovery UI and actual defaults domains still require composition/macOS acceptance as already disclosed; these are not counted again as new findings. No unsafe new unchecked-Sendable use was established in the reviewed store mailbox. The native FSEvents/vnode branches were read, but Linux builds cannot validate their macOS SDK signatures or event lifecycle.
