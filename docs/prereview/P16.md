## Findings, ranked

### P16-1 — Medium — a forward reservation has no terminal path when no journal entry exists

**Locations:** `Sources/HelmOperations/History/WindowOperationHistory.swift:32`,
`:43–47`; `Sources/HelmCore/OperationHistory/OperationHistoryState.swift:40–44`.
Concrete executor boundary: `Sources/HelmOperations/Execute/OperationExecutor.swift:24`.

**Wrong:** after beginForward, the adapter can release the reservation only with
a completed JournalEntry. There is no pre-execution failure/cancellation completion
or direct result completion. Yet execution can return `.busy` before journal.begin,
and planning/context collection can throw before execution starts. The former
returns a real OperationResult whose ID has no journal entry. Following the README's
begin/execute/read-journal/complete sequence then leaves the history permanently
busy, blocking unrelated future forward work and undo. The Core reducer also
requires an OperationID for a no-mutation forward termination. This is distinct
from the intentional block after uncertain/partial mutations.

**Failing scenario:** beginForward for a valid command; have its context builder
throw CancellationError before calling execute. All filesystem mutation spies
remain at zero. There is no public actor method to settle that admitted request.
Separately, reserve forward work and call an executor already busy with retained
work: execute returns `.busy`, journal.entry(result.id) is nil, and no legitimate
completed entry can be passed to completeForward. After the existing operation
settles, history still reports busy. No fake successful/failed journal record
should be necessary merely to release a never-started operation.

**Exact fix:** add a request-matched terminal transition for forward work proven
not to have entered execution, with no required operation ID. Expose it through
WindowOperationHistory and clear forwardCommand exactly once, preserving redo
invalidation and the displayed failure/cancellation. For executor admission
refusals, accept a typed no-execution receipt or ensure admission refusals have
a genuine journal record; do not manufacture ordinary mutation evidence in the
host. Distinguish reserved/not-started from executing so UI cancellation cannot
release a reservation while native work remains unsettled. Add cancellation,
planning error, executor busy, stale abort, double abort and subsequent-forward
admission tests. Current tests supply completed fixtures for every termination;
they never traverse the no-journal boundary.

### P16-2 — Medium — an unrelated recovery result consumes the current inverse reservation

**Locations:** `Sources/HelmOperations/History/WindowOperationHistory.swift:77–85`;
`Sources/HelmOperations/History/HistoryResultMapping.swift:12–16`.

**Wrong:** complete checks the supplied request, command and whether the result ID
has been seen, but never checks that the result's steps belong to the reserved
inverse before retaining it and clearing inverse. Every undo has command recovery.
HistoryResultMapping detects a step mismatch only while deciding success; a
successful mutation in the unrelated result becomes partial, permanently blocking
the receiving history for reconciliation. It also stores a JournalEntry pairing
the reserved plan with the unrelated result. Thus the adapter accepts and corrupts
its state on a cross-window/wrong-result delivery instead of rejecting it while
awaiting its actual result. This is a defensive admission gap at a public host
boundary, not a claim that the currently absent host already misroutes callbacks.

**Failing scenario:** seed independent histories A and B with distinct copy
operations, reserve undo in both, execute B's inverse, then deliver B's result to
A.complete with A's request (a host that looks up the active reservation instead
of capturing the operation association). Its recovery command matches and its
ID is new to A, so complete returns true. B's successful step differs from A's
step; A becomes reconciliationRequired, and its inverseAttempts contains A's
plan with B's outcomes. The later genuine A result is rejected because inverse
was cleared. Assert false on the foreign completion, unchanged pending/history/
attempts, then successful acceptance of A's real result. Also exercise a foreign
failure result and unrelated step with the same source/destination spelling.

**Exact fix:** bind the execution's OperationID to its history reservation before
completion (with an explicit admission handshake or correlated execution receipt),
then require that ID. Validate ordered outcome step identities/definitions against
the reserved plan before any seenOperations/attempts/state mutation. Preserve the
executor's legitimate empty-outcome pre-admission refusal via an explicit bound
no-execution path; do not silently accept arbitrary empty recovery results. Return
false on unrelated evidence, leaving the legitimate reservation intact. Apply the
same operation binding to forward admission: command equality and entry.id ==
result.id establish internal consistency, not ownership by this reservation.
Current independent-window test only checks an empty second stack; stale-completion
tests change the request ID while reusing a valid result, so neither covers this.

## Safety conclusions and limits (not additional findings)

- F13 retains output identity/kind/token and seeds inverse ownership exclusively
  from that journal evidence. Equal-token/different-object substitutions refuse;
  absent identity cannot be filled by observing the current occupant. K38 passes
  the resulting inverse through unchanged. This does not reopen P8-1.
- F16 preserves CancellationError in both initial and per-step undo validation,
  addressing P12-1. Conditional cancelledBeforeMutation remains clean; ordinary
  cancellation from an entered primitive remains uncertain/quarantining. Existing
  F16 tests cover initial reads, a second inverse read after one success, and
  move/Trash admission. The full Replace trashed-backup substitution regression
  now also covers the earlier P12 coverage recommendation.
- Actor methods contain no suspension and create no tasks. The reservation gate
  serializes a correctly routed window's requests. Window lifetime, text-first
  undo, retaining execution tasks and refresh are explicitly host obligations;
  this portable adapter alone does not establish their native correctness.
- Redo is consistently unsupported, including when redoEntries is nonempty. New
  forward intent clears redo at admission. This deliberately limited behavior is
  documented and permitted by P15 N1; it is not a new finding.
- External changes do not silently authorize stale inverses: executor evidence
  checks still refuse them. The retained refused top entry and absent recovery
  UI are disclosed limitations. Inode reuse, same-object/same-token content edits,
  post-mutation observation versus atomic receipts, tree refusal and native
  conditional-operation unavailability are inherited risks, not repeated findings.
- No new locale/time dependency or explicit quadratic per-entry loop was found
  in the added history code. Mapping is linear in primitive count. Unbounded
  entries/request tombstones/attempts are already disclosed; snapshot retention
  can add copy-on-write cost. No new 100k benchmark claim is made.

   settle without allowing cancellation to release in-flight native work (P16-1).

   reject foreign execution evidence before touching state (P16-2).

   ownership and close atomic-receipt/ABA limits before enabling native mutations.

   clean refusal, successful prefix, and genuinely uncertain effects end to end.

   tab closure, track tasks, refresh affected views, and keep redo unsupported until
   fresh-intent reconstruction is reviewed; portable stack tests cannot certify it.
