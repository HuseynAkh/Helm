## Findings, ranked

### P21-1 — Medium — encoded separator/NUL spellings alias literal percent filenames

**Location:** `Sources/HelmCore/PathPresentation/LexicalLocalPath.swift:7`, `:13`,
`:16`; reconstruction in `Sources/HelmCore/PathPresentation/PathPresentation.swift:71`;
deduplication in `Sources/HelmCore/Sharing/SharingRequest.swift:17`.

**What is wrong:** Authority validation accepts file URLs whose encoded path
contains `%2F` or `%00`. On the installed Foundation, `URL.path` leaves these
escapes in its string, while decoding `%25`. Consequently the new lexical key
cannot distinguish an encoded slash/NUL from a real filename containing the
literal characters `%2F`/`%00`. Reconstructing a file URL from that string changes
the input address. A syntactically accepted projection can emit navigation to a
different, literal-percent pathname. Sharing retains its first URL but silently
deduplicates the distinct second URL. This is an encoding ambiguity in the new
helper, distinct from P18-3's filesystem-dependent symlink normalization.

**Concrete failing scenario:** Construct a directory projection from
`URL(string: "file:///a%2Fb")`. Its leaf becomes `file:///a%252Fb/`, and asking
for navigation with the original URL returns that changed destination. A sharing
snapshot containing `file:///a%2Fb` and `file:///a%252Fb/` retains only one item.
`file:///a%00b` similarly projects to `file:///a%2500b/`. These exact results were
reproduced with the built Core module; no navigation or sharing was executed.

**Exact fix:** Make local-path admission and key construction one fallible parse
of the percent-encoded path (available through URLComponents), splitting on
literal URL separators and decoding each component exactly once. Reject decoded
NUL, embedded slash and decoding failures before producing a key or action. A
literal filename `%2F`, encoded as `%252F`, must remain valid and must not undergo
a second decode. Preserve component bytes and the existing literal-parent policy;
construct output URLs only from successfully decoded components with explicit
directory hints. Route Sharing's duplicated validator through the same admission
policy. Add upper/lowercase escape tests, `%2F`/`%252F`, `%00`/`%2500`, encoded
dot/parent components, spaces, percent signs and non-ASCII round trips. Invalid
addresses must produce no projection/action and must fail sharing construction.

### P21-2 — Medium — canonical Unicode equality admits a different path spelling

**Location:** `Sources/HelmCore/PathPresentation/LexicalLocalPath.swift:15`;
`Sources/HelmCore/PathPresentation/PathPresentation.swift:17`, `:25`, `:47`;
`Sources/HelmCore/Sharing/SharingRequest.swift:8`, `:17`.

**What is wrong:** Keys are Swift Strings compared/hashed using canonical Unicode
equivalence. Lexically different NFC/NFD names therefore compare equal without
any filesystem equivalence evidence. The new segment-membership comparison
accepts a URL with a different byte spelling and returns the existing segment's
URL. Selection deduplication also loses one name, and common ancestry can claim
that two distinct parent directories are the same. Linux filesystems can hold
both spellings; the portable contract cannot assume every mounted filesystem
uses normalization-insensitive name identity. Existing shared ItemID concerns do
not excuse this: the standalone Sharing snapshot accepts URLs directly, and the
new PathPresentation lookup bypasses whole-URL equality.

**Concrete failing scenario:** Supply `/caf\u{00E9}` and `/cafe\u{0301}` as two
URLs. Foundation URL equality says they differ, but Sharing returns one URL.
Build a directory PathPresentation with the NFC URL and request navigation using
the NFD URL: it is admitted and returns the NFC destination. The module-linked
probe reproduced both outcomes. Before F21's path-key membership change, the
whole-URL comparison distinguished these two spellings. Sharing's String-based
deduplication weakness predates F21 but remains in the replacement policy; it is
reported here once, not as a second independent regression.

**Exact fix:** Use a byte-preserving key type (for example component UTF-8 byte
arrays with explicit Hashable/Equatable semantics) for deduplication, membership
and component-prefix comparison. Keep display Strings separate. Do not NFC/NFD
normalize or case-fold unless an explicitly injected filesystem policy proves
the equivalence. Apply that same comparison to Spring's lexical target check.
Add NFC/NFD URL-only tests requiring two sharing entries, rejected cross-spelling
segment lookup, and correct common ancestry. Coordinate any wider ItemID change
with its owner, as already deferred by F21; this fix need not silently redefine
all shared identity types.
