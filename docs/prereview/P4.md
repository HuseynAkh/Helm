## Findings, ranked by severity

### P4-1 — blocker — Search bar names a removed Core type

- **Location:** `Sources/HelmUI/SearchBar/SearchBarModel.swift:45`.
- **Defect:** `let domain: SearchDomain` cannot compile. The current public type is `HelmCore.SearchScope` (`Sources/HelmCore/Search/SearchContracts.swift:5`); `SearchRequest.scope` uses it. Neither imported module declares a `SearchDomain` alias.
- **Failing scenario:** Building HelmUI after enabling its target fails before any search UI can run. This is independent of SwiftUI/macOS SDK availability.
- **Reproduction:** After building HelmSearch with the P4 scratch path, run `swiftc -typecheck -swift-version 5 -I /tmp/build-P4/debug/Modules Sources/HelmUI/SearchBar/SearchBarModel.swift`. Actual diagnostic: `45:21: error: cannot find type 'SearchDomain' in scope`. Repeated after a 60-second wait; same error.
- **Exact suggested fix:** Change that annotation to `let domain: HelmCore.SearchScope`; the four case assignments already match the current enum. Update the stale `SearchDomain.recents` reference in `Sources/HelmUI/Part3-README.md`. Typecheck this adapter and run its scope/request tests against the current Core module.
- **Coverage gap:** The existing Part3 tests exercise the right request values, but are outside the active manifest. Their earlier successful typecheck did not protect against this later contract change. Syntax parsing and the static checker both pass despite this error.

### P4-2 — high — Batch rename performs repeated full planning in the UI render path

- **Locations:** `Sources/HelmUI/Sheets/BatchRenameViewModel.swift:27`, `:39`, `:40`, `:42`; callers at `Sources/HelmUI/Sheets/BatchRenameSheet.swift:26`, `:37`, `:47`.
- **Defect:** `preview`, `validationMessages`, and `canRename` each invoke the full planner independently. A single body evaluation therefore performs at least three whole-selection plans, including occupancy normalization, validation, collision checks and temporary rename-step construction. The 20-row preview cap is applied only after that work. Each text edit invalidates the view again. Invalid names can additionally generate an unbounded eager list of validation messages in the sheet's ordinary VStack.
- **Failing scenario:** Select 100,000 files, open Batch Rename, and type a prefix; each keystroke produces three plans over all selected files on the UI rendering path. Enter `/` and the sheet also attempts to render roughly 100,000 validation strings. The concrete repeated work is established by source inspection; the resulting macOS stall duration has not been measured. This recreates the repeated-computation pattern called out in B-010 and conflicts with the large-folder target in parity P-048.
- **Exact suggested fix:** Produce one immutable evaluation containing plan, first 20 preview rows and validation summary, keyed by the complete inputs. Compute large evaluations off the main actor, debounce edits, reject obsolete generations, and disable Rename until the displayed generation is current. Make all three view reads consume that evaluation; keep complete validation in the plan but cap/paginate displayed issue rows. A host-only debounce cannot fix the current getter design because the leaf still invokes the planner repeatedly when it redraws.
- **Coverage gap:** `testPreviewLimitDoesNotLimitValidationOrPlan` checks 25 items and output counts only. Add a check that one accepted edit performs one evaluation and that an older completion cannot enable Rename. Benchmark large selections on macOS. The README acknowledges host caching as future work, but the current model offers no cached evaluation for the host to supply.

### P4-3 — medium — Frame-name repair steals a later window's valid saved identity

- **Location:** `Sources/HelmApp/SessionRestorePlan.swift:32–40`.
- **Defect:** Repair checks only names already emitted. It can allocate a generated name that belongs to a later valid session window, forcing that later window onto a new name and losing its frame association.
- **Failing scenario:** Restore windows with frame names `["", "HelmMainWindow"]`, holding different tabs. The first window receives `HelmMainWindow`; the second is renamed `HelmMainWindow-2`. The first window now receives the second window's saved frame, while the legitimate owner no longer uses it. `["custom", "custom", "HelmMainWindow-2"]` has the same displacement problem. This affects frame preservation in F-068, architecture §10.3 and parity P-001/P-013.
- **Exact suggested fix:** Precompute a reserved set of all nonempty input frame names. Preserve the first occurrence of each valid name. Allocate repairs against both that reserved set and names already assigned, so repairs cannot claim a later original name. Keep the existing monotonically incremented ordinal search for unused names.
- **Coverage gap:** `testRestorationFallbackAndPreferences` asserts only uniqueness, so it passes while valid names are displaced. Add both input sequences above and assert the originally valid later names remain unchanged. Repro is specified here only; no test file was added.

### P4-4 — medium — Collapsed operation details still format every outcome on every refresh

- **Locations:** `Sources/HelmUI/Operations/OperationsPanel.swift:34–39`; `Sources/HelmUI/Operations/OperationRowModel.swift:35–46`.
- **Defect:** The cheap visibility question `!row.details.isEmpty` eagerly maps every operation outcome into path/error strings. It does so even while Details is collapsed, and repeats whenever the parent redraws (for example, progress from another operation). Expansion calls `details` again and places the entire result into a non-lazy hierarchy. Retaining completed rows, as the integration contract requires, amplifies this cost.
- **Failing scenario:** Leave a completed 100,000-step copy in the panel with Details collapsed, then start another copy. Every progress refresh re-formats the retained copy's 100,000 outcomes. Expanding it attempts to build all detail rows. The source guarantees the repeated formatting; macOS frame-time and memory impact still need measurement.
- **Exact suggested fix:** Test `row.result?.outcomes.isEmpty == false` to decide whether a disclosure exists. Give the disclosure explicit expansion state and format/render details only while expanded. Use a virtualized List or paginated detail view with stable outcome identities, and cache formatted immutable outcomes so unrelated progress does not repeat formatting.
- **Coverage gap:** Existing leaf tests verify small outcome strings and failure wording, not collapsed-state work or large-result rendering. Preserve those assertions and add a large-result UI measurement with a second operation updating.
