## Findings, ranked by severity

### P12-1 — Medium — undo token validation converts clean cancellation into a changed-source failure requiring reconciliation

**Locations:** `Sources/HelmOperations/Execute/OperationExecutor.swift:213–214`
(`validateExpectedSource`), `:99–107` (failure classification), and `:46`
(initial expected-token validation). Recovery refusal is at
`Sources/HelmOperations/Undo/UndoPlanner.swift:10–12`.

F13 moves read-only validation outside `StepExecutionFailure`, but the token
validator still catches every metadata error and throws `.sourceChanged`.
Consequently a `CancellationError` from that read never reaches the new clean
cancellation classification. `.sourceChanged` takes the default
`uncertain = true` branch even though no mutation wrapper exists. This produces
`requiresReconciliation == true` for a step whose primitive was never entered.
The executor remains usable, but UndoPlanner refuses to reverse any completed
steps in that result. This is an incomplete P8-2/F13 repair, not a recurrence of
the fixed unconditional quarantine at conditional admission.

**Concrete failing scenario / proposed regression:** execute two independent
leaf moves and build their real journal inverse. Use a forwarding filesystem
adapter that allows all initial evidence reads and the first inverse move. At
the second inverse's `validateExpectedSource` read, suspend on a gate, cancel
the executing task, then have the read honor cancellation with
`Task.checkCancellation()`. The source and destination of this second move are
unchanged and its conditional mutation spy has zero calls. Nevertheless the
result error is `.sourceChanged(secondSource)` and that outcome requires
reconciliation. Building an inverse of this partial inverse returns a stopped
plan, preventing automatic reversal of the successfully completed first move.
Expected: `.cancelled`, no reconciliation for the unentered primitive, retention
of the first success, and eligibility to plan reversal of that success with its
recorded evidence. An unrelated create on the same executor should still work.

An even smaller variant cancels the first read in the initial expected-token
loop: line 46 also converts cancellation into `.sourceChanged`, and line 50
does not override an existing failure. That variant misreports cancellation but
does not itself set a reconciliation flag because every step is not attempted.

**Exact fix:** preserve `CancellationError` before the generic catch in
`validateExpectedSource`; let it reach the outer cancellation mapping with no
`StepExecutionFailure`. In the initial validation loop, classify cancellation
explicitly as `.cancelled` before applying the existing changed-source fallback.
Keep ordinary mutation cancellation wrapped and quarantining, and keep genuine
identity/token mismatches refused. Do not fix this by treating all mutation
errors as clean or by relaxing identity checks.

**Why the existing test passes:**
`F13CancellationTests.testReadOnlyValidationCancellationDoesNotQuarantine`
executes a forward copy with no expected tokens. Its injected second source
read throws from `ForwardEvidence.validate`, which preserves cancellation.
Copies do not enter `validateExpectedSource`, so that test passes with the
remaining catch-all intact. Add the gated inverse-move and initial-loop cases
above alongside the existing uncertain-primitive control.

## Safety conclusions and regression sensitivity

- **P8-1's reported replacement attack is repaired.** Outcomes retain identity,
  kind and token; UndoPlanner carries final surviving output evidence into the
  inverse; ForwardEvidence does not acquire inverse ownership from current
  occupants. Initial checks compare all expected outputs before mutation and
  each destructive primitive supplies recorded evidence to conditional admission.
  Missing identity fails closed. Same-token/different-identity create/copy/move
  substitutions and installed/backup replacements are meaningfully tested.
- **Clean admission is distinct from uncertain completion.** The fake emits
  `cancelledBeforeMutation` before its evidence check or effects, with no await
  inside admission/mutation. The ordinary `CancellationError` path remains wrapped
  and quarantines; no reviewed production path translates an uncertain mutation
  failure into the new clean case. A provider falsely throwing a no-effects error
  after writing would violate the provider contract; that hypothetical is not
  counted as a new implementation defect. Existing quarantine is never cleared
  by the new branch: quarantined executors refuse at entry.
- **Replace coverage has a boundary worth extending.** F13's replacement fixture
  manually performs copy → old-target-to-backup → stage-to-target. It omits the
  production plan's backup-to-Trash step. The separate Trash test checks a valid
  round trip, not substitution. Add a complete planner-produced Replace test
  substituting the actual trashed backup with equal token/kind and a different
  identity before inverse construction and before execution; require zero inverse
  effects. These current tests would not catch a future Trash-specific identity
  adoption bug. Current shared evidence code does protect that path; this is a
  coverage recommendation, not another established bypass.
- **Trash restore / Put Back and cross-volume:** journal restore uses the actual
  returned Trash URL and requires the recorded original to match the step's
  source. The origin alone does not authorize undo: journal evidence is still
  required. Pure PutBackPlanner supplies destinations, not a mutation receipt or
  proof of object ownership. Native Trash location/volume behavior remains
  unverified. Cross-volume Move still uses copy/verify/Trash; undo restores the
  recorded trashed source before retiring the copied output, with conditional
  evidence at each destructive step. A cross-volume restore that cannot use the
  same-volume move primitive refuses rather than weakening admission. The fake's
  single `memory` volume does not certify native cross-volume behavior.
- **Previously reported limits are not new findings.** Post-mutation metadata
  observation is still not an atomic completion receipt; same-object/same-token
  content changes and descendant evidence remain unresolved; directory/package
  undo remains refused. Live conditional copy/move/Trash still inherits
  unsupported refusal. F13 adds no native implementation or macOS SDK-specific
  API, and does not close those earlier P6/P8/P11 limitations. No additional
  unsafe Sendable use, ownerless task, or new 100k algorithmic regression was
  established in the eight changed production files.
