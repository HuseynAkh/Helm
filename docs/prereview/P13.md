## Findings, ranked by severity

### P13-1 — Medium — successful retry resets the recovery budget through automatic rebind

**Locations:** `Sources/HelmFileSystem/Loading/DirectoryEffectRunner.swift:64`,
`:71`, `:92`; `Sources/HelmCore/State/TabReducer.swift:62`.

**Wrong:** The three-attempt budget belongs to one invocation of `watch`.
Every successful retry emits a synthetic `rootChanged`. Successful validation
then unconditionally cancels that newly started watch and emits `startMonitor`
with a new generation. That starts another three-attempt budget at attempt zero.
Thus the adapter/store combination does not bound one automatic recovery
episode, even though each individual invocation is bounded. It also discards a
working replacement watch solely because its startup was a retry.

**Concrete failing scenario / proposed test:** Use the real WindowStore and
DirectoryEffectRunner over an accessible in-memory directory. Have the factory
return monitors whose odd-numbered starts throw and whose even-numbered starts
succeed and remain open indefinitely. Gate retry sleeps explicitly. Start one
watch, with no later user action or filesystem event. Start 1 fails; start 2
succeeds; the synthetic root event validates successfully; the reducer cancels
2 and creates 3. Start 3 fails; 4 succeeds and is replaced by 5, indefinitely.
The default delay repeatedly returns to 250 ms; it never reaches exhaustion.
Each cycle adds directory reads and snapshot publication. Assert that recovery
retains a usable watcher or reaches an episode-wide bound, and that shutdown
cancels a gated sleep without another factory invocation. Current code fails
the bounded/stable recovery assertion.

**Exact fix:** Distinguish reconciliation after establishing a fresh watch from
validation that invalidates an existing native root binding. Successful retry
must reconcile, but must not automatically discard the replacement solely for
the synthetic recovery event. Preserve a recovery-attempt budget across any
automatic validation/rebind still needed in that episode. Reset it only after
an explicitly defined stable recovery or explicit user retry, not merely on a
new watch generation. Keep independent cancellation/lifetime identities so
closing or superseding the owner terminates the whole episode.

**Test sensitivity:** `testRepeatedFailuresAreBoundedAndRetireWatch` calls the
runner directly and always fails startup; it never exercises reducer-driven
rebinding. `testRecoveryThroughStorePublishesAndRebindsThenReceivesChange`
fails only the first start and lets all later starts succeed. Both pass with
the feedback loop above. F14's per-lifetime bound is locally true but
insufficient for its recovery/storm objective.

### P13-2 — Medium — failed validation strands a recovery event already received during its read

**Locations:** `Sources/HelmCore/State/TabReducer.swift:58`, `:62`, `:101`,
`:106`; replay helper at `Sources/HelmCore/State/TabNavigation.swift:85`.

**Wrong:** F14 defers ordinary changed/rescan events while validation is pending
by setting `monitorDirty`. On validation success it rebinds and replays that
dirty state. On failure it only sets `monitorNeedsValidation`; it emits no
reconciliation even when `monitorDirty` already records a newer event. Waiting
for the next event loses the recovery notification that arrived during the
failed read. No cancellation or stale-generation issue is needed.

**Concrete failing scenario / proposed test:** Keep a watch active. Deliver
`unavailable(.permissionDenied)` to admit validation V. V observes a transient
read failure; hold its callback. Restore access and create a file, then deliver
the resulting rescan while V is still pending. The reducer records dirtiness
without starting another read. Deliver V's failure through its captured store
callback. The tab remains failed, dirty and needing validation, with zero new
work. With no further writes, it never discovers the accessible directory or
new file. Use `unavailable`, rather than a sticky coalescer root invalidation,
so the subsequent ordinary event remains ordinary. A gated runner test can
assert exactly one follow-up validation and eventual fresh contents; also
assert no retry is emitted after a failure with no intervening event.

**Exact fix:** At accepted validation failure, retain validation priority and
consume/replay any dirty invalidation accumulated during that request once,
when active and not loading/staging/degraded. Clear that consumed dirtiness
when admitting the follow-up. If foreground work or staging defers it, preserve
it for the existing terminal replay. Do not unconditionally retry failures:
without a newly recorded invalidation, remain failed and idle. This provides
event-driven recovery without introducing an error-only retry loop.

**Test sensitivity:** `testOrdinaryEventDoesNotSupersedePendingValidation`
asserts only that work is deferred; it never completes validation.
`testValidationRetiresAlreadyQueuedReloadSuccessAndFailure` tests failed V but
does not put an ordinary event between V admission and completion. Both pass
when the deferred recovery event is stranded. This is a new consequence of
F14's validation-priority gate, not a repetition of P9's staged-navigation or
inactive-tab findings.

## Other reviewed risks and limits

- WindowStore captures request identity before callbacks arrive; queued old
  reload success/failure is rejected after validation supersession. The direct
  legacy action bypass is explicitly disclosed by F14 and is not counted again.
- Explicit tab disposal, monitor cancellation and shutdown retain the watch
  task's cancellation handle. Default backoff uses cancellable Task.sleep and
  checks cancellation before creating a replacement. No additional confirmed
  timer-after-close defect was established. Add gated close-during-backoff and
  unmount-during-recovery tests; the existing recovery tests do not prove them.
- Attempt UUID checks protect adapter success/cleanup; watch generations and
  work generations protect store admission. No new counter-reuse defect was
  established in normal tab lifecycles. Test late old-attempt failures alongside
  a new attempt and subsequent watch-generation replacement on Mac.
- F10's snapshot worker still indexes off MainActor and avoids a second sort.
  The already disclosed reducer resort when options change remains; no new
  100k-entry timing guarantee is inferred from Linux tests. P13-1 increases
  repeated work even when each build is correctly off-main.
- Persistence's missing-file classification, dirty-load guard and serialized
  revision-checked saves remain unchanged. No new persistence corruption
  finding was established; one-instance-per-document and explicit flush remain
  composition requirements.
- Native vnode event flags/identity and FallbackMonitor termination changes
  require macOS 14 SDK and runtime acceptance. Linux does not compile the
  Darwin branch. No speculative SDK failure is reported as confirmed.
