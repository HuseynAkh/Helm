## Findings, ranked

### P20-1 — Medium — inverse binding accepts a different verification policy and ownership evidence

**Location:** `Sources/HelmOperations/History/WindowOperationHistory.swift:53–56`,
with completion at `:112–118`; effect at
`Sources/HelmOperations/Execute/ForwardEvidence.swift:18–39`.

**Wrong:** the new inverse admission handshake compares command and ordered
steps, but ignores `undoVerification`, `expectedTokens`, `expectedKinds`,
`expectedEvidence`, issues and context. A reconstructed plan can preserve every
StepID/step definition while defaulting away the journal ownership constraints.
It passes binding and executes with those weaker constraints. Completion then
stores the *reserved* plan alongside results produced by the different plan and
can pop the original entry. This is a defensive host-boundary defect: the README
requires unchanged execution, and a correct host obeying that requirement is
safe. No currently wired native host is claimed to make this mistake.

**Concrete failing scenario:** execute and register a real New File operation at
`/target/new`, then reserve undo. Another actor replaces that file with a different
object. A host reconstructs the plan as
`OperationPlan(command: undo.plan.command, steps: undo.plan.steps)`, inadvertently
using defaults for the other fields, and passes this same reconstructed plan to
execute and bindExecution. Binding returns true. With InMemoryFileSystem's
conditional mutation provider, ForwardEvidence now takes the forward/default
path, observes the replacement occupant, and the Trash step can retire it.
The bound ID and exact step list pass complete; the recorded inverse attempt
incorrectly claims the original leaf-only evidence was used. The genuine reserved
plan would refuse the replacement identity. No forged result is required.

**Exact fix:** before setting `execution`, require semantic equality of the entire
reserved inverse plan, including verification policy, all three expected maps,
issues and every context field used by execution. Implement an explicit comparison
or suitable value conformances; do not equate plans by step IDs alone. Alternatively
make the execution boundary consume an opaque reserved plan and always execute
that stored value. Add admission regressions changing each safety field separately,
plus the replacement-occupant scenario above: rejected binding, zero mutations,
unchanged pending/attempts, followed by legitimate terminal settlement. This is
distinct from P16-2's unrelated result/operation-ID matching, which F19 repairs.

### P20-2 — Medium — an undo cancelled before binding has no no-execution terminal transition

**Location:** `Sources/HelmOperations/History/WindowOperationHistory.swift:62–66`,
`:89–104`, `:109–114`; Core action surface in
`Sources/HelmCore/OperationHistory/HistoryContracts.swift:50–58`.

**Wrong:** F19 adds a preparation abort for forward work and makes inverse
completion require a bound execution. An undo reservation has no corresponding
preparation abort. After beginUndo returns, cancellation of the host before
execute/bind leaves `inverse` and `state.pending` installed indefinitely. Neither
abortForward nor complete can settle it. The caller must enter an executor solely
to manufacture a terminal execution for work it has already decided not to start,
or discard the entire window history. The README's post-binding cancellation
rule does not cover this pre-binding window.

**Concrete failing scenario:** register one completed file creation; call
beginUndo; suspend the host before dispatching its execution task. Cancel the
command/window task and have its normal `Task.checkCancellation()` exit before
execute. No primitive or journal.begin has run. abortForward returns false because
the pending reservation is undo, and a cancellation OperationResult cannot pass
complete's new binding guard. All subsequent beginForward/beginUndo calls are
refused as busy even though no operation remains in flight. Existing preparation
cancellation tests exercise only forward work.

**Exact fix:** add a request-matched abortUndo (or unified abortPreparation) that
is accepted only while the inverse has no bound execution. It must clear inverse
and pending, retain the original undo entry and existing redo state, record the
failure/cancellation, and reject stale/double aborts. Keep abort and bind atomic
within the actor: if abort wins, subsequent binding must return false and prevent
mutation; if bind wins, abort must return false and the retained task must settle
normally. Add both race orders, cancellation before task launch, subsequent
admission, and duplicate/stale abort tests. This extends F19's phase model to
inverse preparation; it does not repeat P16-1's repaired forward/busy-journal gap.

## F19 dispositions and safety checks

- Forward preparation abort is request-matched and single-use; after binding,
  execution cannot be released by abort. Genuine busy refusals now have complete
  per-step journal evidence and can release a bound reservation without adding
  an undo entry. P16-1's concrete forward scenarios are addressed.
- Bound operation IDs and exact ordered steps reject foreign recovery success,
  foreign failure and malformed empty results before retaining attempts or clearing
  pending. Duplicate completion cannot consume a later reservation. P16-2's
  concrete cross-window completion scenario is addressed; P20-1 concerns the
  earlier plan-admission boundary instead.
- A forward journal with nil result cannot enter history. A forward still pending
  prevents beginUndo. Failed/no-change forward completion does not create an undo
  entry. Partial/uncertain completion retains evidence but sets reconciliation,
  which prevents undo admission. No new path to undo an honestly reported,
  unfinished forward operation was established.
- Executor sets its running gate before journal/admission suspension. Busy callers
  do not clear it. Cancellation after successful mutation retains that success;
  normal executor terminal paths produce one outcome per planned step, satisfying
  the new strict completion check. Host task retention remains necessary.
- Core public types remain Core-owned, explicitly initialized where applicable
  and Sendable. No new Apple-only dependency was found in the reviewed additions.
  Native conditional mutation refusal, atomic output receipts, tree undo refusal,
  redo, durability, unbounded retention and reconciliation UI remain previously
  disclosed limitations, not additional findings.
