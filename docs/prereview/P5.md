## Findings, ranked by impact

### P5-1 — Medium — A pre-refresh monitor result can overwrite the newer listing

**Locations:** `Sources/HelmCore/State/TabReducer.swift:44`, `Sources/HelmCore/State/TabNavigation.swift:17`, `Sources/HelmFileSystem/Loading/DirectoryLoadPipeline.swift:33`.

Monitor snapshots carry only the watch generation and location. `startLoad` increments only the load generation. After that load finishes, a snapshot from an earlier monitor reload still passes every monitor acceptance guard. The loader's UUID only distinguishes requests within that pipeline; the documented separate foreground and monitor pipelines do not invalidate each other. The store forwards the original generations faithfully, so it cannot repair this ordering.

**Failing scenario (text repro):** Start a monitor reload for `/a` with hidden files enabled, holding its result just before delivery. Toggle hidden files off; finish the resulting foreground load with only visible files. Deliver the held monitor snapshot with the unchanged monitor generation and `/a` location. `isLoading` is now false, so the reducer publishes the hidden entries despite `showHidden == false`. An ordinary refresh similarly permits older metadata/deleted entries to replace newer results.

**Exact fix:** Give monitor reload requests an identity containing the watch generation and current load/options epoch, carry it in their results, and reject results whose epoch differs from current state. Increment that epoch on foreground reload, navigation and hidden-option changes; cancel associated monitor reload tasks as well. An alternative is to retire/restart the watch generation on every foreground reload, with explicit cancellation of its auxiliary reload work. Cancellation alone is insufficient for already queued results.

**Missing test:** Existing stale-monitor tests change location/watch generation; the loader integration test runs load and reload sequentially. Add the held-result sequence above, asserting final IDs and hidden visibility, not just presentation revision. This is the same stale-callback class addressed by B-014 and architecture Fix 13.

### P5-2 — Medium — A monitor update during a foreground load can be lost permanently

**Locations:** `Sources/HelmCore/State/TabReducer.swift:44–52`, `Sources/HelmCore/State/TabNavigation.swift:69–70`.

Monitor events are allowed while `isLoading` is true once navigation has committed. They launch `refreshPaths`, but the resulting monitor snapshot is discarded while loading. Neither rejection nor load completion records/replays the outstanding change. This is distinct from P5-1: even rejecting all older monitor results correctly does not recover a newer update dropped during loading.

**Failing scenario (text repro):** A large directory load has captured an early batch containing `x`. Delete `x` externally after that batch. The monitor emits a change; the separate reload finishes quickly and correctly excludes `x`, but its snapshot reaches the reducer while the original load remains active and is dropped. The original cumulative load then finishes with its previously captured `x`. No further filesystem event occurs, so `x` remains displayed indefinitely. The sequence is also possible immediately after the first navigation batch starts monitoring.

**Exact fix:** Track a pending monitor invalidation/dirty flag while loading. Coalesce these events instead of launching snapshots that will be discarded. On the current load's terminal success or failure, issue one fresh reload of the committed location and clear the flag when that request is scheduled. Preserve the flag when a superseding load is for the same location; retire it with the old location on navigation. Combine this with P5-1's result identity.

**Missing test:** Drive `.monitorEvent`, `.monitorSnapshot` and `.loadFinished` in the order above and assert a follow-up `.refreshPaths` effect and eventual removal of `x`. Current coalescer-to-reload tests only use an idle tab. This defeats F-008 live refresh despite the B-016 quiet-window/max-age fix.

### P5-3 — Medium — A retained unavailable event suppresses subsequent refresh and root validation

**Locations:** `Sources/HelmFileSystem/Loading/DirectoryReloadCoalescer.swift:29`, `:72`; `Sources/HelmCore/State/TabReducer.swift:54`.

`revalidation` is never cleared and includes `.unavailable`. Every later changed/rescan publication is replaced with that failure. Unlike rootChanged/unmounted, the reducer's unavailable branch only publishes an error; it emits no validation/restart effect. The README's assumption that composition revalidates/replaces the watch is therefore not expressed by this effect interface. Moreover, unavailable can replace an undelivered rootChanged event in the one-element buffer, removing the only request for validation.

**Failing scenario (text repro):** Receive `.unavailable(.timedOut)`; consume its error action. Let the provider recover and receive `.changed(paths: ["/a/new"])`, advance FakeClock past the quiet window and flush. The next action is still unavailable, with no refreshPaths effect. Repeating any number of ordinary changes never recovers. A second sequence is rootChanged followed by unavailable before consumption: only the non-validating failure survives.

**Exact fix:** Keep root revalidation and watcher error as separate pending state; an error must not demote a pending root revalidation. Add an explicit acknowledgement/reset after validation, or emit a reducer effect that retires and replaces the failed watch/coalescer. Ensure a recovered provider's subsequent changes schedule a refresh. Do not simply clear the marker immediately on yield, which would reintroduce the slow-consumer overwrite this code was intended to prevent.

**Missing test:** Extend `testMonitorQuietWindowMaximumAgeAndStickyRoot` with failure→recovery and rootChanged→unavailable→slow consumption, checking reducer effects. The current test establishes stickiness but never demonstrates recovery.

### P5-4 — Medium — Refresh does not refresh an active search

**Locations:** `Sources/HelmCore/State/TabReducer.swift:31–33`; `Sources/HelmCore/State/TabNavigation.swift:86`; `Sources/HelmCore/State/TabSearch.swift:5`.

`.refresh` only calls `startLoad`. With a search overlay active, the accepted load updates `underlyingSnapshot`, leaving the visible search results and search generation unchanged. There is no `.startSearch` effect. The old `ContentViewController.refreshDirectory()` at lines 201–215 explicitly reruns `updateSearchQuery` when a query is active, and F-008 requires that behavior.

**Failing scenario (text repro):** Complete search Q with result `old`; remove that file and add another matching file after a finite search provider has completed. Send `.refresh`, then deliver the refreshed directory listing. The overlay still shows `old`, no new search request exists, and Cmd+R cannot recover it.

**Exact fix:** When refreshing with a nonnil search, restart that query through `startSearch` (cancelling and advancing the search generation) as well as refreshing the underlying directory. Preserve the original underlying selection/snapshot ownership. The existing `restart` helper already contains the query-restart pattern; reuse or extract it so Refresh and hidden-setting reloads behave consistently.

**Missing test:** Refresh *after* search has completed and assert a new generation plus `.startSearch`, reject old-generation results, then accept fresh results. `testSearchPreservesUnderlyingSelectionAndLoadCannotOverwriteOverlay` starts its refresh *before* starting search, so it does not test this requirement.
