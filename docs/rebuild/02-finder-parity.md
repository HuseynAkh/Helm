# Helm as a Finder replacement: feature parity catalogue (02-finder-parity)

Draft completed by Astra (codex), 2026-11-04, from Fable's untouched partial. Pending Opus review after 10 PM Toronto time on November 4, 2026. This is a catalogue and proposed disposition, not authorization to implement integrations, send files, change defaults or sharing, or perform destructive actions.

Evidence precedence: owner instructions; `review-01-architecture.md` fixes over `01-architecture.md`; `00-current-state.md` Appendix C and `00b-opus-review.md` over the audit body; source for current static behaviour. The original brief is `/workspace/forge/runs/p1_parity.v2.txt`. No network or macOS runtime verification was used. Finder targets below describe the macOS 14 baseline; version-sensitive shortcuts, system integration and API signatures remain handoff checks.

## 0. How to read this document

**Scope.** Finder capabilities on macOS 14 that a personal power user could notice, grouped by area, plus the macOS integration questions that decide whether "replacement" is even possible. The catalogue is deliberately exhaustive (several hundred rows) so that later phases can pick from it rather than rediscover it.

**Columns.**

| Column | Meaning |
|---|---|
| ID | `P-nnn`, stable, cited by later phases. |
| Item | Short name. |
| What Finder does | The exact observable behaviour, including shortcut, as a target to match or consciously deviate from. |
| Helm today (legacy app audit baseline, not current rebuild completion) | `Yes`, `Partial`, `No`, citing `F-xxx` (features) and `B-xxx` (bugs) from the Phase 0 audit and `M-xx`/`C-xx` from the Opus review. "Yes" means reachable and roughly right, not bug-free. |
| Pri | `P0` must-have for a daily-driver replacement; `P1` important, expected within the first year; `P2` nice-to-have, parity for completeness, or consciously deferred. |
| Cx | Build complexity under the macOS-blind authoring constraint: `S` under a day of model work, `M` a few days, `L` a week or more, `XL` a multi-week subsystem or one that needs real-Mac iteration. |
| APIs | macOS APIs involved. Public API candidates for macOS 14; undocumented formats and uncertain signatures are explicitly identified as compatibility research, not supported contracts. |
| Modules | Where the work lands in the `01-architecture` package: `Core` (`HelmCore`), `FS` (`HelmFileSystem`), `Ops` (`HelmOperations`), `Search` (`HelmSearch`), `Persist` (`HelmPersistence`), `UI` (`HelmUI`), `App` (`HelmApp`). |
| Notes / pitfalls | What will bite, what to verify on a Mac, and where Helm should deliberately differ. |

Priority is urgency; disposition is separate. P3 is not currently used. “Not planned” is not encoded by P2; exclusions and other dispositions belong in the separate G0 coverage ledger (03 §6). Keep nine columns.

**Priority rule of thumb.** P0 is "I would go back to Finder within a day without it". P1 is "I would go back within a month". P2 is "I would shrug".

**Uncertainty.** Platform claims inferred from memory or local plans are not verified documentation. Specific high-risk claims are marked `[Needs verification on macOS]`. Current Helm behaviour is static source evidence, not a successful runtime test; inherited Yes entries for system-provided features mean delegated support, not tested parity.

**Helm identity constraints (from the audit §4.7 and 00b §5.5)** that this catalogue respects rather than overrides: Cmd+L typed-path address bar, explicit Cut/Paste that moves, Cmd+D toggles Star, Starred and Recent as first-class Places, `~/Templates` New File, grid and list as the primary views, batch rename modes, "Properties" naming, always-visible status bar. Where Finder parity conflicts with one of these, the row says so and proposes an alias or a setting rather than a silent replacement.


**Architecture corrections governing every row.** Module abbreviations retain the original nine-column format. Monitoring is in FS, not a new module. AppKit providers and platform UI belong in UI: `ApplicationProvider`, `PropertiesEnricher`, `VolumeEventSource`; FS owns `VolumeReader` and attribute reads (review Fix 3). Core owns `ItemSort`, query/result values and common IDs, with no reverse dependency (Fixes 1, 5, 16). Persist uses Foundation and broadcasts; Combine adapters live in UI (Fix 4). Ops and FS access persistence through injected protocols, never a direct Persist import (Fix 2). A row listing both modules describes cooperation, not a new dependency edge. Proposed new types such as `TagStore` and saved-search codecs are future additions, not existing architecture declarations.

Search remains an overlay in `TabState.search`; a proposed tag or smart-folder place supplies a query rather than silently extending the current `Location` enum (Fix 5). Keep custom tabs and disable automatic window tabbing for the initial rebuild (Fix 48); native tabs are an alternative requiring a separate architecture decision. File undo uses the journal directly through split-controller command routing, with text undo left to AppKit (Fix 35). Reload widgets and restore selection/anchor first; animated batch updates wait for Mac validation (Fix 44). Folder merge is deferred; Replace remains replacement with staging and recoverable old contents (Fix 42).

**Verification environment.** The old briefs' “no Swift on Linux” statement is superseded: Swift 6.0.3 is available via `source /workspace/toolchains/env.sh`, in Swift 5 language mode, tools 5.9 (ADR-011). For rebuild target status, see the current as-built record; for code changes, compile and test them on Linux; filter selects tests to run, not targets to build, so the manifest must exclude Mac targets there (review Fix 7). This documentation-only task does not create targets or test artifacts. AppKit, Launch Services, File Provider and Finder behaviour still need a Mac.

### 37.2 Default file manager: feasible scope and hard limits

A useful replacement can own daily browsing, file operations and explicit folder-open requests. There is no established public switch that transfers all Finder responsibilities to Helm. The distinction matters: a successful Launch Services folder association is not proof that Reveal in Finder, Desktop, Dock Trash, AirDrop discovery or Finder extensions have moved to Helm.

The current `Helm/Helm/App/Info.plist:41-55` already registers `public.folder`, role `Viewer`, `LSHandlerRank = Alternate`. That is an observed declaration of candidacy, not an observed default association. The app's external-open implementation is incomplete (F-002, B-018/B-103/B-114). Fix routing before offering any default-manager experiment. A bare SwiftPM executable does not carry the bundle registration (B-007).

## 40. What NOT to do

- Do not use private Finder, DesktopServices, AirDrop, MobileDevice or File Provider host interfaces; do not inject code, swizzle Finder or install SIMBL-like hooks. Finder Sync extension development is not permission to host every extension inside Helm.
- Do not disable SIP, change sealed-system files, bypass TCC, modify its databases or ship an always-root file manager. Full Disk Access is not a substitute for ownership permissions or a supported privileged-operation design.
- Do not kill Finder repeatedly, disable its launch agent, replace its Dock identity or change CreateDesktop behind the owner's back. Keep the Desktop and system Trash available through their normal owners.
- Do not mutate Launch Services associations, Finder defaults, shared favourites, synced tag dictionaries, .DS_Store or sharing configuration at launch. Read-only private-format experiments are optional research, not a production dependency; bounded parsers and fixtures are required before even an import claim.
- Do not use shell-string interpolation for filenames, URLs or passwords. Invoke fixed executables with argument arrays and their documented input contracts. A password option taking argv is not made safe by attaching stdin; do not implement speculative encrypted ZIP plumbing.
- Do not follow symlinks while recursively planning copies/deletes, remove an old destination before its replacement exists, confuse cloud eviction with deletion, or empty Trash based on guessed timestamps. Every supported mutation needs a concrete target, partial-result accounting and the stated undo/confirmation policy.
- Do not fabricate Finder parity from a system API name. A successful open request is not completed mounting, an AirDrop sheet is not delivery, local provider completion is not remote sync, and an index miss is not proof that no matching file exists.
- Do not adopt native tabs, new keyboard bindings, AppKit in Core/FS, Combine in Persist, a Search-to-Persist dependency or an async UndoManager bridge just because the partial suggested one. The architecture review fixes win; proposed additions need declared types and explicit module boundaries.
- Do not count a Linux Foundation compile as macOS API verification. Use the available toolchain for actual core logic after targets exist, in Swift 5 mode; run Mac checks for UI, filesystem fidelity, TCC, provider and Launch Services behaviour.
- Do not send/share files, run workflows, change default handlers, administer volumes, publish or perform paid work as part of drafting. All described integrations are future capabilities; owner approval must name any actual external action. Opus review remains pending after 10 PM Toronto on November 4, 2026.
